## 2026-09-04 10:33 — `gsim-wasm` bindings implemented: real wasm-bindgen surface, no longer just `version()`

Built the wasm-bindgen bindings `crates/gsim-wasm` had been missing since Phase 1 completed
(`crates/gsim-wasm/src/lib.rs` previously exported only the `version()` smoke test). Same task
scope as the parallel `gsim-py` PyO3 work (a sibling agent, not directly coordinated with) —
both expose the same JSON contracts so a frontend (`general-simulator-gui`) and a Python caller
end up able to do the same operations.

**Interface design, as mandated**: stateless JSON-in/JSON-out free functions, not a stateful
`#[wasm_bindgen]` struct wrapping `ModelBuilder` across the FFI boundary — avoids JS-side
lifecycle management (explicit `.free()`, leak/double-free risk) for a first pass; matches this
crate's own philosophy of JSON as the interchange format everywhere. 13 functions plus the
existing `version()`: `evaluateComponent`, `validateParameters`, `newModel`, `addBlock`,
`removeBlock`, `setParam`, `addModelParam`, `connect`, `autoArrange`, `loadDocument`,
`saveDocument`, `placeWithoutOverlap`, `layeredLayout` — camelCase JS names via
`#[wasm_bindgen(js_name = ...)]`, semantics identical to the spec (no deviations). Every
fallible function returns `Result<String, JsValue>`, throwing a real JS `Error` object (via
`js_sys::Error::new(...).into()`, not a bare string) with the underlying Rust error's `Display`
message. `connect`'s error message is verified (by test) to name the specific failure case —
cross-paradigm / dangling endpoint / duplicate id — not a generic failure, since
`docs/specs/gsim-sch-format.md` §8.3 needs the frontend able to give immediate red-X feedback
specifically for the cross-paradigm case.

**A real host-testability gap found and worked around, not papered over**: `wasm-bindgen`'s
`JsValue`/`js_sys` bindings are backed by actual JS imports that exist only on the `wasm32`
target — constructing *any* `JsValue` at all (even `JsValue::from_str`, not just
`js_sys::Error::new`) on the host test target panics at runtime
("function not implemented on non-wasm32 targets"), confirmed by first writing the natural
version of this crate (thin `#[wasm_bindgen]` functions with all logic inline) and watching
11 of 22 tests SIGABRT on `cargo test`. Since host-target `cargo test` is this crate's mandated
primary verification path, restructured every fallible function into a private `*_impl`
returning `Result<String, String>` (touches no wasm-bindgen type, fully testable on host) plus a
one-line public `#[wasm_bindgen]` wrapper that only calls `.map_err(js_err)` — the sole place in
the file that ever constructs a `JsValue`. Tests call the `*_impl` functions directly, asserting
on plain `String` error messages; the public wrappers' `Ok` path (which never touches `JsValue`)
is exercised directly where convenient (`version`, `new_model`, the full-flow test). This is a
wasm-bindgen-crate-level constraint, not a `gsim-core` API gap — no `gsim-core` change was
needed for this.

**No `gsim-core` API gap found**: every mandated function mapped directly onto an existing
`gsim-core` public function/type (`contract::evaluate_component`/`validate_parameters`,
`document::{Model, ModelBuilder, GsimSchDocument, Endpoint, ConnectOptions, NewBlockSpec}`,
`layout::{place_without_overlap, layered_layout, Rect, Axis, LayoutInput}`) with no awkward
shape requiring a new helper on the core crate.

**Verification**:
- `cargo test --workspace`: 55 gsim-core (40 unit + 15 fixture integration, unaffected) + 22
  gsim-wasm (new) + 0 gsim-py — all passing. Covers the mandated flow (`new_model` ->
  `add_block` x2 -> `connect` -> `auto_arrange` -> `save_document` -> `load_document` round
  trip) and one real error case per fallible function (bad JSON per function, duplicate block
  id, invalid rotation, unknown block on `set_param`, dangling wire endpoint, cross-paradigm
  connect with message-content assertion, duplicate wire id, non-v2 schema version, invalid
  axis string, `auto_arrange` defaulting a missing bbox to `(0,0)` rather than erroring).
- `cargo clippy --all-targets -- -D warnings` and `cargo fmt --all -- --check`: both clean.
- **wasm32 actually verified, not just host `cargo test`**: both `wasm-pack` (0.13.1) and the
  `wasm32-unknown-unknown` target were already installed. Ran
  `wasm-pack build --target web` from `crates/gsim-wasm` — real release-profile compile to
  `wasm32-unknown-unknown` plus `wasm-opt`, succeeded cleanly (`pkg/` generated, then deleted —
  it's gitignored, a build artifact, not a checked-in one). Confirmed via the generated
  `pkg/gsim_wasm.d.ts` that all 13 functions plus `version()` are present with the exact
  camelCase names above and `string`-in/`string`-out signatures (`i64` params became TS
  `bigint`, expected from wasm-bindgen's default i64 mapping — no additional JS-side glue coded
  or needed for this pass).

**What remains**: same as noted after Phase 1 completed — the frontend
(`general-simulator-gui`) doesn't consume this package yet; that integration (wiring
`primitive-renderer.ts` to call `evaluateComponent` instead of its existing per-mechanism
drawing code, and the `.gsim_sch` editor to call the document/builder functions) is separate,
unscoped work.

## 2026-09-04 10:17 — Full code-integration family fixtured; port-id stability fixed

User asked to (1) find every other array-length-driven component beyond Sum/Product (naming
cscript/python/octave as a hint), (2) re-confirm the four bugs from the previous session are
really fixed, (3) actually solve the port-id-stability limitation rather than just documenting
it.

**(1) Component survey**: pulled the full component list from `general-simulator`'s
`component-reference.md`. Found `general-simulator` has **five** code-integration kinds sharing
one identical `inputs=`/`outputs=` dual-variadic-port shape: `CScript`, `PyFunction`, `PyBlock`,
`OctFunc`, `OctBlock` (only the last two were fixtured last session). Added
`extensibility.cscript`/`.pyfunc`/`.pyblock` — deliberately not claimed as new *engine* coverage,
since they're structurally identical to the already-tested octfunc/octblock shape; added for
taxonomy completeness, which is what was actually asked. Also found `Counter` has a genuinely new
pattern along the way: optional ports gated by whether a *string* parameter is non-empty at all
(`up_down=`, `reset=`), not an enum value or array length — added `control.counter` to cover it,
using `when: "${{ params.up_down != '' }}"` per optional port. Confirmed no separate vector/bus-
width-driven block exists beyond what's already covered. `Discrete State-Space` is structurally
identical to `StateSpace` (matrix-dimension-driven) — noted in the taxonomy backlog, not
fixtured, same "no new pattern" reasoning.

**(2) Bug re-confirmation**: all four bugs from the previous session (`for_each` delimiter
stripping, `"0.0"` loop-index formatting, integer-vs-float `==`, cross-parameter defaulting) were
already fixed with regression tests in commits `b9cd690`/`a9f460d`/`4fdf3ca`. Verified those
specific tests are still in the suite and passing; no rework needed.

**(3) Port-id stability — actually fixed, not just documented**: the original decision-0001
wording ("index-based and stable") overclaimed. The real fix: author the driving parameter as an
**array of objects each carrying its own persistent `id`** (e.g. `operands: [{"id": "s1",
"sign": 1}, ...]`), bind `for_each`'s `as` directly to each object, and reference `${{
operand.id }}` in `emit` instead of a loop index. This needed **zero engine changes** — dotted
field access on a `for_each`-bound value was already general, just never demonstrated end-to-end.
Added `control.sum.stable_ids` and
`stable_id_pattern_survives_removing_an_interior_operand`, which removes the *middle* operand
(not the tail) and proves the surviving operands' port ids are byte-identical to before. Updated
`docs/decisions/0001-scope-and-naming.md`'s port-identity section to state the real, narrower
guarantee (bare array/string: append/trim-at-end only) alongside the now-proven mitigation
pattern, rather than leaving the overclaim standing.

**Verification**: 55 tests total (40 unit + 15 fixture integration, up from 52), `cargo clippy
--all-targets -- -D warnings`, `cargo fmt --all -- --check` — all clean, no new engine bugs found
this pass (the closed builtin whitelist already covered everything these needed).

**What remains**: unchanged — `gsim-py`/`gsim-wasm` bindings still only export `version()`;
`Discrete State-Space`/`Discrete Transfer Function`/PWM-modulator/waveform-source/table-lookup/
flip-flop/SR-latch/hysteresis/VCO/PMSM/Clarke-Park-family taxonomy entries remain un-fixtured
(same "no new structural pattern" reasoning as before — real cataloguing work, not engine work).

## 2026-09-04 10:04 — 4 more fixtures for `general-simulator`'s newest commits

The user updated `general-simulator` since Phase 1 completed (six new commits,
2026-08-31..09-04); read all of them to stay current. Two were directly relevant to
`gsim-core`:

- **`general-mna` renamed `Sig2Voltage`/`Sig2Current` -> `Sig2Phys{domain}`, `Probe` ->
  `Phys2Sig`** (commit `9c02d80`, consumed here). Confirmed `gsim-core` never referenced the old
  names anywhere committed, so nothing needed correcting. The rename itself validates a design
  choice already made here: `Sig2Phys`/`Phys2Sig` are exactly instances of the GUI's
  `paradigm: converter` concept (`docs/specs/gsim-sch-format.md` §8's `physical-signal` port
  kind, bridging acausal physical-network and causal signal-flow) that `Paradigm::bridges_paradigms()`
  already models in `document::builder`.
- **`kind=octfunc`/`kind=octblock`** (commits `2f0352b`, `e6a13cb`) — new Octave-hosted script
  block kinds, called via a persistent `octave-cli` subprocess (deliberately never linked
  in-process, to keep this MIT project clear of GPLv3 Octave). A genuinely new component family:
  open-arity `inputs=`/`outputs=` rather than a fixed parameter set.

Added 4 more real fixtures, each proving something the first 8 didn't cover:

- `converter.sig2phys` — a `paradigm: converter` component with a `domain: voltage|current`
  enum param, bridging a `signal` port to a `physical-electrical` port.
- `converter.phys2sig` — **zero input ports** (matches the real component exactly: "Zero
  block-graph inputs, it reads the circuit's own previous-step operating point directly") — the
  first fixture with an empty `ports:` list — plus a real mutually-exclusive-parameter rule
  (`node` XOR `branch`, `${{ (value != '') != (params.branch != '') }}`), the first
  cross-parameter validation testing something other than an ordering constraint.
- `extensibility.octfunc` / `extensibility.octblock` — **two independent variadic port groups
  in one component** (`input_names` and `output_names` each drive their own `for_each`,
  unrelated in length/content) — not exercised by any of the first 8, which each had at most one
  variadic group. `octblock` adds a validated `xc_count >= 0` integer param on top of the same
  port shape.

All 4 passed on first run, no new bugs found this time (the closed builtin whitelist and
cross-parameter defaulting fix from the previous session's authoring already covered everything
these needed).

**Verification**: 52 tests total (40 unit + 12 fixture integration, up from 8), `cargo clippy
--all-targets -- -D warnings`, `cargo fmt --all -- --check` — all clean.

**What remains**: same as before — `gsim-py`/`gsim-wasm` bindings still only export `version()`;
none of Phase 1's real surface (GSF v2, `.gsim_sch` document/builder, autolayout) is exposed to
Python or the frontend yet. Netlist compilation (including whatever `kind=octfunc`/`octblock`
would need on that side) remains out of Phase 1 scope.
