## 2026-09-04 14:42 — Goto/From lowering: implicit connections resolved into direct references

`docs/specs/gsim-sch-format.md` §10's Simulink-style implicit connection (a `routing.goto`
broadcasts its `in` driver under a string tag; a `routing.from`, with no wire input at all,
resolves to the Goto sharing that tag) was **half-built across two repos and finished in
neither**. `general-simulator-gui`'s `apps/frontend/src/canvas/goto-from-resolver.ts` has a
real, tested implementation of the *resolution* algorithm, but its one call site
(`GotoFromOverlay.tsx`) uses it purely to draw a dashed hint line — it never rewrites the
model. On this side, `compile/spec.rs` had no registration for either type at all
(`routing.ground` was the whole `routing.*` family), so compiling any schematic using them hit
`CompileError::UnknownType`. This entry closes that.

**Where the pass runs, and why there.** Inside `build_scope`, at the very end — after
`Outputs` is recorded and before any `NetlistTarget` can call `ref_name`. Two facts forced
this position. First, `general-simulator`'s `kind=` grammar does **not** store block-name
references in a block's own params: a `field=` reference is derived at emit time from *wire
adjacency* (`Scope::peer_of` → `Scope::ref_name`). So there is no "field value" to rewrite in
a pre-pass; the substitution has to happen where the peer endpoint is chosen. Second, the
chase needs `Outputs`, because `peer_of` prefers a peer that is a known output when a port
carries several wires (the chained fan-out convention). Hooking it here means every `field=`
shape — `in=`, `inputs=`, `ctrl=`, `gate=`, `RefsIndexed`, an `X` card's positional
connections — picks up the substitution for free, and one hook covers future targets too.

**How substitution works.** `compile::routing::resolve_scope` does the §10 matching and
returns `from id -> goto id`. `resolve_from_sources` then walks one step further, to whatever
is wired to the matched Goto's `in` port, and stores `from id -> real driving Endpoint` on the
new `Scope::from_source`. `ref_name` applies it to the peer it just found, *before* the
`SubcktDef` boundary check and the vector-output check, so those see the real source. Chasing
is a loop, not one hop: a Goto's own driver may be another `From` (a Goto rebroadcasting a tag
it received), which is legal and does occur. `routing::Chase` guards it, so a tag that closes
back on itself is `CyclicFromTag`, not a hang. Concretely, for
`CMD -> KGATE -> Ggate[GATE_CMD] ... Fgate[GATE_CMD] -> GATE`:

```
before (what a naive emitter would write)   GATE kind=sig2phys domain=voltage in=Fgate
after  (what is actually emitted)           GATE kind=sig2phys domain=voltage in=KGATE
```

`examples/tagged_gate_goto_from.py` asserts the strongest form of this: the same circuit
rebuilt with real wires and *no* routing blocks compiles to a **byte-identical** netlist.

**Registration.** Both types are `structural: true`, which `emit_scope`'s existing
`if spec.structural { continue; }` already honours — the same mechanism `routing.ground` and
`spice-subckt.boundary` use — so neither reaches the netlist. `routing.from` does declare
`output_ports: &["out"]`, though: a From *is* a driver as far as wire adjacency goes, and
without a recorded output it would lose `peer_of`'s driver preference on a fanned-out port.
The recorded name is never emitted; `ref_name` substitutes before it can be read.

**Visibility — a deliberate, documented limitation, not a silent one.** §10.1 gives a Goto
`local` / `scoped` / `global`. All three are accepted; **all three currently behave
identically**. `gsim-core` has no subsystem hierarchy: `Block` has no parent field and
`ModelBuilder` has no `add_subsystem_block` (`hierarchy.subsystem.*` is in the spec catalogue
and nowhere in this crate). Every block in a scope therefore shares the same — absent — parent,
which makes the frontend resolver's `local` test (`gotoParent === fromParent`) trivially true
for every pair, and its `scoped` ancestor test likewise. Implementing the distinction means
building subsystem nesting, which was explicitly out of scope for this task. So the namespace
is flat *per compile scope* — and a `SubcktDef` body is a real independent scope, which is the
one scoping distinction this crate can make honestly today, since `build_scope` runs
per-scope. Revisit when `Block` gains a parent; the resolution shape deliberately mirrors the
TS resolver's so that adding a `visible_to` predicate is the only change needed. Written up in
`compile::routing`'s module doc so a future session does not re-derive it.

**Kind restriction.** §10.2 partitions tags by port-kind and forbids acausal kinds outright.
The port-kind of a routing block is taken from the `kind` of a wire touching it (§8.4 makes
that authoritative), falling back to the block's own `domain` when it has no wire — an unused
From or a stub Goto still gets checked. Routable kinds are the causal ones (`signal`,
`signal-bus`, `function-call`, `physical-signal`); anything else is `RoutingKindUnsupported`,
whose message points at named nets (§9) as the correct alternative. Note `nets.rs`'s existing
`is_physical_kind` was **not** reused: it is a `physical-` *prefix* test, which would sweep in
`physical-signal`, and §10.2 names that kind explicitly as a second, independent tag namespace.
Candidate matching compares tag *and* kind, so `signal:"CLK"` and `physical-signal:"CLK"` are
two clean pairs rather than one ambiguity.

**Errors.** Four new `CompileError` variants, keyword-mapped in `gsim-py` like every other one:
`UnresolvedFromTag` / `AmbiguousFromTag` (§10.3's two hard errors, message wording matching the
spec's `Unresolved From tag "<tag>"` / `Ambiguous From tag "<tag>"`), `CyclicFromTag`, and
`RoutingKindUnsupported`. A Goto nobody reads stays fine (§10.3: a stub is not an error) — but
a Goto that *is* read and has nothing wired to its `in` reports `UnconnectedRef` against the
**Goto**, not against the far-away consumer, which is where the author actually has to look.

**Proof.** Nine unit tests on the resolution algorithm itself (single/unresolved/ambiguous/
blank tag/kind-partitioned/wire-kind-outranks-domain/acausal rejected), seven end-to-end
compiler tests including the rebroadcast chain and the self-closing loop, and
`examples/tagged_gate_goto_from.py` run against the real binary: a 24 V chopper whose gate
command reaches the switch only through a tag, `V(SW) = 23.976024 V` against the closed-switch
0.01 Ω / 10 Ω divider (an unrouted gate would leave the switch open and V(SW) at 0).

## 2026-09-04 14:13 — Per-block comments, authored in Python, emitted into the `.cir`

A block can now carry free-text annotation that survives the whole way from schematic
authoring (`gsim-py`'s `add_block`) into the compiled netlist text, as real SPICE comment
lines next to that block's own card.

**Shape: two independent `Vec<String>` slots.** `Block.comment_before` and
`Block.comment_after` (mirrored on `NewBlock`, `NewBlockSpec` and `NewSubcktInstanceSpec`,
and on `gsim-wasm`'s shadow struct so the JSON contract stays identical across bindings).
Two slots, not one — above and below are genuinely different intents and a block may want
either, both or neither. `Vec<String>` rather than `Option<String>` because a real authored
comment is usually several lines and the emitted form is line-oriented; the existing
`label: Option<String>` was the pattern for *optionality*, not for cardinality.

**Emission.** `compile::general_simulator::with_comments` wraps each emitted card in
`comment_lines(...)` — one `* {text}` line per newline-delimited line, `*` alone for a blank
one. Full-line `*` is the only comment form `general-mna`'s lexer accepts regardless of
dialect, and it is what this emitter's own two header lines have always used; no inline
end-of-line form (`$`, `//`, `;`) was invented, since those are dialect-specific and buy
nothing here. `emit_scope`'s `elements`/`blocks` vectors now hold **one entry per block that
may itself span several lines**, so the comment stays glued to its card across the
`lines.extend(elements); lines.extend(blocks);` regrouping — the previous "one entry = one
line" assumption would have scattered them.

**Coverage, and one deliberate omission.** Plain element cards, `kind=` block cards, both of
those inside a `.subckt` def body (shared `emit_scope`), and `X` cards via `emit_x_card` (a
subckt instance *is* a `Block`, so `instantiate_subckt` threads the same two slots). Left
out: `emit_nested_instance`, whose input is a `SubcktInstance` rather than a `Block` and so
has no comment fields to thread — adding them there would be new schema surface with no
caller. A block emitting *both* sub-grammars (an ideal switch: an element card plus a
`kind=` card) gets its comment on each card, because the two land in different groups and
are never adjacent; annotating only one would leave the other unexplained.

**Found by running, not reading.** The first version accepted only a JSON array, so the
natural Python spelling `comment_before="loop gain\nre-tuned after the step test"` failed
with `invalid type: string ... expected a sequence`. `deserialize_comment` now takes either
a string or an array; storage stays the array form, and an entry that still contains `\n`
is split at emit time, so both spellings produce byte-identical netlists.

**Verification.** Five new unit tests (four in `general_simulator.rs` covering element
cards, `kind=` cards + the embedded-newline split, the dual-card duplication, and def
bodies + X cards; one in `block.rs` for string-or-array acceptance and for empty slots
staying out of the serialized document). Full gates green: `cargo fmt --check`, `cargo
clippy --workspace --all-targets -D warnings`, `cargo test --workspace --exclude gsim-py`
(98 + 28 + 31), `cargo test -p gsim-py --no-default-features` (26).

End-to-end: new `examples/annotated_rc_comments.py`, built through a real `maturin develop`
and actually run, asserting placement *positionally* (the line directly above/below each
card) rather than "the text appears somewhere", plus the exact total `*` count so a comment
can neither leak onto an uncommented neighbour nor be silently dropped. Its real output is
checked in as `annotated_rc_comments.cir`:

```
Vin n_R1_p1 0 5
* series element of the RC low-pass
* 1 kohm with C1 -> f_c = 159 Hz
R1 n_R1_p1 n_C1_p1 1000
* (tolerance is not modeled here)
C1 n_C1_p1 0 1e-6
* storage element -- ic defaults to 0 V
* loop gain
* re-tuned after the step test
K1 kind=gain k=2.5 in=U1
U1 kind=const value=1
```

`general-simulator` is not installed in this environment, so the script's optional solver
step reported "compiled only, not run" — the one claim not backed by a run here, mitigated
by the emitted form being the same `*` header lines every already-verified example netlist
carries.

**Not touched:** there is no `docs/specs/gsim-sch-format.md` in this repo (the source tree
references it, but the file itself lives outside), so there was no schema reference doc to
add the fields to.

## 2026-09-04 13:34 — Registry completion: five more families, four bugs in the *old* ones, four real runs

Closes the "what remains" list from the 12:15 entry. Every field spelling below was re-read
out of the real source in this session — `general-mna/src/system_builder.rs`'s own `build_kind`
arms and `general-simulator/crates/continuous-blocks/src/coordinate_transforms.rs` — rather
than carried over from the earlier reading, precisely because a wrong field name produces a
netlist that never runs.

**Families added** (`compile::spec::REGISTRY`, 11 → 27 types):

| GSF v2 type | `kind=` | verified against |
| --- | --- | --- |
| `control.state_space` / `.discrete_state_space` | `statespace` / `discretestatespace` | `system_builder.rs` `"statespace"`/`"discretestatespace"` arms |
| `control.transfer_function` / `.discrete_transfer_function` | `tf` / `discretetf` | same file, `"tf"`/`"discretetf"` arms |
| `control.transform.{clarke,clarke_inv,park,park_inv,clarke_park,clarke_park_inv}` | `clarke`/`clarkeinv`/`park`/`parkinv`/`clarkepark`/`clarkeparkinv` | `coordinate_transforms.rs`'s `call`/`input_count`/`output_names` |
| `machine.pmsm` | `pmsm` | `system_builder.rs` `"pmsm"` arm |
| `extensibility.{cscript,pyblock,pyfunc,octfunc,octblock}` | same names | each family's own arm |

**Three source-verification surprises.**

1. **`kind=cscript` takes `lib=`, not `path=`.** It names a precompiled shared object, not a
   source file. Everything else in the family takes `path=`. The GSF v2 fixture had it right
   all along (`extensibility.cscript`'s parameter really is `lib`) — this is exactly the field
   the 12:15 entry warned would "silently produce a netlist that fails to parse."
2. **`KindName::PerVariant` is not what the transform family needs.** GSF v2 already gives each
   transform its own dotted type with its own port names, and `system_builder.rs` matches six
   distinct `kind=` strings with no selector parameter anywhere, so the mapping is one
   `KindName::Fixed` per type. The variant enum stays in the code with still no user — a
   genuine "designed for a case that turned out not to exist" note, left rather than removed
   because a family shaped that way may still show up. `outputs=` **is** emitted for all six,
   because the implicit default names come from `CoordinateTransform::output_names()` and those
   disagree with GSF v2's port ids: `control.transform.park`'s third *output* pin is `zero_out`
   (its `zero` id being taken by an input), so leaving the names implicit would make the drawn
   port and the netlist symbol disagree.
3. **Neither state-space arm parses an `outputs=` field at all.** A MIMO system is *one*
   `SignalValue::Vector` under the block's own name. But the GSF v2 contract still draws
   `out0..out{q-1}` pins, so a document can wire the second one — and a bare block-name
   reference would then silently mean "the whole vector" rather than "element 2". New
   `TypeSpec::vector_output` + `CompileError::VectorOutputPort` reject that. This is the same
   class of bug as the 12:15 entry's `MissingSymbol` find, except worse: it would have
   *simulated*, just not the circuit that was drawn.

**Four bugs found in families that were already registered.** The 12:15 entry described the
entries beyond those the acceptance circuit itself needed as "the unambiguous signal-flow
families" — but none of them had ever been run, and four had the wrong field spelling.
`general-mna` reads `in=` and `inputs=` per family, from `fields` directly, and they are not
interchangeable:

- `control.gain`, `control.vco`, `logic.hysteresis` emitted `inputs=` where their arms read
  `in=`;
- `power.pwm1` (`kind=pwm`) did too — only `pspwm` takes a three-entry `inputs=` list — *and*
  read its duty from a port called `duty` where the GSF v2 fixture's input pin is `in`;
- `control.saturation` emitted `lower=`/`upper=` where `BlockKind::Saturation`'s netlist form
  is a single symmetric `limit=`.

All five are `device '<name>' missing field 'in'` at load time rather than a mis-simulation, so
nothing silently wrong ever shipped — but they were five netlists that could never have run.
The registry now carries a `# `in=` versus `inputs=`` section naming which arm each entry came
from, so the next addition has to answer the question rather than assume.

**Two new registry mechanisms**, both forced by families whose port *count* is per-instance
(GSF v2 models them with `for_each`-generated pins, so a `&'static [&'static str]` cannot
express them): `Arity` (`ParamLen` over `input_names`/`output_names`; `MatrixCols` over `b`'s
own column count, honouring `parse_matrix_or_vector_shorthand`'s flat-vector SISO shorthand)
and `FieldSpec::RefsIndexed` / `TypeSpec::dynamic_outputs` built on it. A hole in an indexed
`inputs=` list is `CompileError::IndexedRefArity`, never a short card. Matrix parameters needed
no new rendering at all: `render_value` already emits `[[1,2],[3,4]]`, which is exactly what
`parse_matrix_rows` accepts.

**Nested `.subckt` emission**, the other gap the 12:15 entry left open. A `SubcktDef` whose body
instantiates another def now writes real `X<name> <connections> <DEF>` cards inside its own
`.subckt`/`.ends` block, for both spellings that reach it: a body `Block` carrying a
`subckt_ref` (connections derived from the body's own wires) and a `SubcktInstance` in
`def.instances` (connections already names in the body's namespace, as in a hand-written nested
X card). A wrong connection count is a hard error rather than a short card.

**Four real `general-simulator` runs — the actual proof.** All four circuits are original and
synthetic, written for this purpose; none reproduces or adapts a published reference design.

- `examples/buck_state_space_pi.py` — a 24 V/12 V/5 Ω buck at 100 kHz regulated by a **MIMO
  state-space PI**. Rather than needing a summing block the registry has no entry for, the
  compensator takes `[ref, measurement]` as two inputs and forms the error itself
  (`a=[[0]] b=[[ki,-ki]] c=[[1]] d=[[kp,-kp]]` *is* a PI controller with the integrator as its
  one state) — which is also what makes it a real test of the `inputs=` list whose length comes
  from `b`'s column count. The measurement path runs through a `kind=tf` single-pole filter.
  **400000 steps clean, V(VOUT) settled 12.1516 V against a 12 V reference, duty 0.4979 against
  the open-loop ideal 0.5.** The first gains tried (ki=800) *ran clean and looked settled at
  5 ms* and then diverged into duty saturation by 20 ms — a reminder that "the run exited 0" is
  not the same as "the loop is stable"; the committed gains were picked by sweeping and
  checking the 20 ms tail.
- `examples/pyblock_buck_control.py` — the same power stage with a **Python** controller:
  `kind=pyfunc` feedforward (`d = Vref/Vin`, plus a headroom output), a stateful `kind=pyblock`
  slew-rate limiter as soft start, and a `control.gain` consuming the pyfunc's **second** output
  by its generated name `FF_headroom`, so a wrong second-output name is a hard `MissingSymbol`
  rather than a silent no-op. `inputs=REF,VINM` order is load-bearing: reversed, the duty would
  be `Vin/Vref = 2`. **200000 steps clean, V(VOUT) 11.9820 V, SLEW 0.5000, HEAD 12.0000 V.**
  Needed a simulator rebuilt with `--features python` (the plain binary answers
  `PythonSupportNotCompiledIn`), and the run happens from a space-free temp dir because the
  embedded interpreter cannot resolve a path through this checkout's own directory name — the
  same workaround `general-simulator-cli`'s own tests carry.
- `examples/nested_subckt_ladder.py` — a four-section RC delay line as two levels of reuse:
  `SECTION` (R + C), `STAGE` (two `SECTION` instances and **nothing else** — a body made purely
  of nested X cards, exactly the shape the old emitter dropped silently), two `STAGE` instances
  at the top. **20000 steps clean, V(VOUT) 3.57143 V = 5 × 10k/14k**, the exact divider through
  all four sections. An open `STAGE` would have left it at 0.
- `examples/floating_reference_bridge.py` — §9's reference-net fallback, **run** rather than
  unit-tested, closing the last gap the 12:15 entry flagged. No `routing.ground`, no
  `is_reference` net; the return rail has 6 endpoints against 5/3/2 so the heuristic must pick
  it, and it *must* be right because an MNA system with no reference row is singular.
  **1000 steps clean, V(TOP) = 12.000000 V, V(MID) = 6.000000 V**, exactly the 100 Ω / 4×400 Ω
  divider, plus the mandated info-level note.

**`cscript`/`octfunc`/`octblock` are registered but unit-tested only**: `cscript` needs a
compiled `.so` and the Octave pair needs a linked Octave, neither of which an example in this
repo can produce portably. Their field shape is `pyblock`/`pyfunc`'s, which *was* run.

**What remains**: `simulation` directives are still round-tripped as opaque JSON and never

(`source.voltage.dc`, `passive.*`, `source.dependent.*`, `control.gain`,

particular are now registered with a port id (`in`) taken by convention from every other
single-input fixture rather than from a contract of their own, which is exactly the sort of
gap that produced the four field-spelling bugs above. `converter.phys2sig`'s `node=`/`branch=`
are plain parameters, so a document using one has to know the emitted net name and pin it with

MIMO state-space outputs past the first are rejected rather than addressable, which is faithful
to the engine but means a multi-output state-space can only feed a block that accepts a vector.

## 2026-09-04 12:15 — Phase 2 opened: netlist compiler, verified by a real `general-simulator` run

Built `crates/gsim-core/src/compile/` — the netlist compiler
`docs/decisions/0001-scope-and-naming.md` explicitly deferred out of Phase 1. Three modules:
`nets.rs` (net resolution), `spec.rs` (the per-type emitter registry), `general_simulator.rs`
(the first `NetlistTarget`), plus `compile(model_json, target)` in both bindings.

**The dual grammar.** `general-simulator`'s netlist format is two genuinely different
sub-grammars in one file, and which one a block gets depends on its paradigm:
(1) real SPICE element syntax, `NAME node1 node2 [node3 node4] value_or_model_ref`, positional
nodes resolving to shared net names; (2) `spice-lsp/docs/GRAMMAR.md` §12's block syntax,
`NAME kind=<value> field=value ...`, no device letter, no node list, every `field=value` either
a literal or a **direct reference to another block's name**, never a net. One `TypeSpec` can
declare **both**, because an ideal switch really is emitted as a pair in the real netlist:
`DEV d s idealswitchmodel` supplying the nodes, plus
`DEV kind=ideal_switch r_on=... gate=block ctrl=GATE` supplying the fields.

**Three load-bearing rules, each verified against real source rather than memory:**

- **The device letter is the first character of the element's name.** Read
  `general-mna/src/builder.rs`'s stamping loop directly: it dispatches on
  `element.device_letter` with `R`/`C`/`L`/`V`/`I`/`G`/`E`/`F`/`H`/`K`/`D` each stamping a
  different device and anything else rejected. A resistor whose block id is `snub1` is not a
  resistor to this target at all, so `spec::element_name` prefixes the required letter when the
  id lacks it.
- **A bare block-name reference means that block's *first* output** — confirmed in
  `general-mna/src/block_graph.rs`'s own `output_names` docs: `output_names[0]` aliases the
  block's own name. Later outputs need their own name, read from the block's own `outputs=`
  param where its type declares one, else that family's documented default — for `pspwm` that
  default is `[name, "{name}_comp"]`, taken straight out of `system_builder.rs` rather than
  guessed.
- **Some families expose one `kind=` per function/variant**, not a generic type + selector
  param (`kind=clarke`/`kind=park`, never `kind=transform type=clarke`). `KindName::PerVariant`
  exists for exactly that, kept per-family rather than assuming one shape fits all.

**Net-naming scheme chosen** (`docs/specs/gsim-sch-format.md` §9 prescribes the *character set*,
`^[A-Za-z_][A-Za-z0-9_]*$`, and the reference-net fallback, but not a generator): explicit
`wire.net` wins; else, inside a `SubcktDef` body, the `.SUBCKT` card's own boundary port name
(which is what an `X` card substitutes into positionally); else `n_<block>_<port>`. The
reference net is a `routing.ground` block or a `nets[]` entry marked `is_reference`; with
neither, §9's own mandated behaviour applies — pick one heuristically (largest net) and emit an
info-level note rather than erroring.

`nets.rs` is the **first Rust port of `gsim-model/connectivity.py`**, and carries over the
two-pass named-net fix that file documents as a real bug it hit (a name recorded against
`find(from)` mid-loop goes stale when a later `union` reparents that very root) — with a
regression test that fails on a single-pass implementation. Two deliberate differences: only
`physical-*` wires make nets (a signal wire is a block reference, not a node — unioning them
would invent nodes the target grammar cannot express), and generated names derive from the
**lexicographically smallest endpoint** rather than the order-dependent union-find root, so an
unrelated edit doesn't churn every net name in the emitted file.

**One real bug, found by running the output rather than reading it.** The flat example first
failed with `Evaluate(MissingSymbol("Dlega_high_G"))`: a switch whose block id lacked the `D`
letter emitted `Dlega_high d s idealswitchmodel` next to `lega_high kind=ideal_switch ...`.
`general-mna` joins the two lines **by name**, and its diode stamping introduces the symbol
`<name>_G` that the `kind=` card's entry must resolve — so the element card and its `kind=` card
must share one name. Fixed with `spec::card_name` (used by both emitters *and* by output
naming), plus a regression test quoting the real error. This is exactly the class of bug that
looks right on the page and isn't, and it is why the acceptance bar was a real run.

**Two real errors in the committed example**, also found by checking it back against the
hand-written reference rather than trusting it: a transformer secondary return/AC midpoint
node was wired to the wrong reference, shorting it to ground, and the VCVS's controlling
nodes are its own `cp`/`cn` ports, not a param. Added an explicit `routing.ground` block
tying primary and secondary reference together the way the hand-written reference does, so
the reference is declared rather than heuristic.

**The acceptance test — the real proof.** A `.subckt`-based reproduction of a real multi-leg
power-electronics reference circuit (kept out of this repo per
`docs/decisions/0002-no-private-content.md` — the reproduction itself lives in the private
project it was drawn from) compiled cleanly and ran through the real `general-simulator`
(built from the sibling repo, `cargo build --release -p general-simulator-cli`):

```
general-simulator <compiled netlist> --mode transient --tfinal 3e-4 --dt 2e-8
exit 0, no stderr, 15001 rows, 55 columns, 2.3 s
```

The emitted file was structurally line-for-line equivalent to the hand-written reference
netlist — same `.subckt` shape, same device/model/converter bodies, same six positional `X`
cards, same E/F transformer pair — differing only in net *names*. It did **much** better than
the README's "right order of magnitude" hypothesis:

```
signal      max |gen - ref|      gen rms
I(Vdc)          2.5e-11 A        12.57 A
```

## 2026-09-04 11:51 — True SPICE `.subckt` reuse: define once, instantiate many

Built the "subschematic" mechanism the 11:14 entry named as *not* buildable yet — but
**not** via `hierarchy.subsystem.*` (`docs/specs/gsim-sch-format.md` §11), which embeds a
full copy of a nested model per block instance and is therefore the wrong tool: it cannot
express "one definition, many instances with different external connections." The right
concept already existed, designed but never ported to Rust:
`packages/gsim-model/src/gsim_model/subckt.py` in `general-simulator-gui`
(`SubcktPort`/`SubcktInstance`/`SubcktDef`/`CyclicSubcktDefError`/`check_no_cyclic_defs`),
read in full — along with its `tests/test_subckt.py` and the hand-written reference netlist
for a real multi-leg power-electronics circuit — before writing anything.

**New `crates/gsim-core/src/document/subckt.rs`**, plus `Model.subckt_defs`,
`Block.subckt_ref`, `ModelBuilder::add_subckt_def`/`instantiate_subckt` +
`NewSubcktInstanceSpec`, and matching `gsim-py`/`gsim-wasm` bindings.

**Divergence 1 — structured body, not opaque text** (mandated, and confirmed correct):
`gsim_model.SubcktDef.body` is raw SPICE text, "readable verbatim but not decomposed into
blocks/wires". Fine for *its* purpose; wrong here, because the entire point is
programmatic construction through `gsim-py` (which cannot emit opaque text) and eventual
visual rendering / GSF v2 validation (which cannot inspect it). So `SubcktDef` carries
`blocks`/`wires`/`instances`. **Verified against the real circuit, not assumed**: every
element card in `sw_leg_fixed`/`bidir_sw_fixed` (`ideal_switch`, `pspwm`, `sig2phys`, plain
`R`/`C`) maps onto an existing GSF v2 fixture (`passive.switch.ideal`, `power.pwm2`,
`converter.sig2phys`) or an existing block type. Nothing in a real subckt body needs to be
opaque.

**Divergence 2 — the `ctrl_*` signal-port question, resolved by widening the restriction.**
`gsim_model` restricts `SubcktPort.kind` to the four acausal physical-network kinds. The
real `sw_leg_fixed`'s port list is `d s ctrl_freq ctrl_phase ctrl_duty`, and the three
`ctrl_*` nets are **signal**-kind (`FSW_CONST`/`PH_DQ*`/`DUTY_ALL`, all `kind=const`
signal blocks at the top level) — outside that restriction. The alternative considered and
**rejected**: fold the `ctrl_*` inputs into the def body as internal constant blocks. That
fails on the real circuit, because the four `X_DQ1..4` instances share one def but each is
handed a *different* phase — internalising them would need four near-identical defs,
destroying exactly the define-once/instantiate-many property this whole module exists for.
So `signal` is now an allowed `SubcktPort` kind here. `physical-signal` stays rejected, for
the same reason `gsim_model` gives (a converter *bus* type, not a real net kind — a subckt
boundary is never a converter). The reference implementation never had to answer this
because its bodies were opaque text with no structural port-kind checking at all.

**Two smaller design calls the structured body forced, that the reference never faced**:
- *How does an internal wire reach the def's own boundary port?* A `Wire`'s `Endpoint` is
  always `(block, port)`; there is no third endpoint kind. Rather than add one (every
  `Wire` consumer would then have to handle it), the convention is a **boundary
  pseudo-block inside the body whose id is the def's own id**, type
  `spice-subckt.boundary`. The body stays a self-consistent mini-model — every wire
  endpoint resolves to a real block, nothing dangles by the ordinary rules — and no new
  type was needed. `SubcktDef::boundary_endpoint()` names the convention in code.
- *`Paradigm::SpiceSubckt` now bridges paradigms*, for the same reason `Hierarchy` does: a
  `.SUBCKT` boundary has no paradigm of its own, and a real one genuinely mixes
  `physical-electrical` and `signal` boundary ports. Without this, every mixed-boundary
  subckt would be unwireable. (This is `SpiceSubckt`'s first real use — the variant existed
  but was unused.)

**Cycle detection** ported faithfully (white/gray/black DFS over the `def_ref` graph, same
"dangling `def_ref` is a separate schema-level concern" handling, same
`"Cyclic SubcktDef reference: a -> b -> a"` message format), with one implementation change:
made **iterative**, so a deep def chain cannot blow the Rust stack where the Python
reference would only hit its own recursion limit. `add_subckt_def` validates id/port kinds
*before* the push and **rolls the push back** if the whole-list cycle check then fails —
fail-before-mutating-state, matching the reference's own stated philosophy and this crate's
`CrossParadigm` precedent. Cases covered: self-reference and mutual 2-cycle (the two the
Python tests considered important), plus a 3-cycle, a dangling ref (must *not* be a cycle),
and a diamond (a def reachable by two paths must not be mistaken for a cycle — this is what
the black colouring exists for, and the reference's tests never covered it).

**The real acceptance test: a `.subckt`-based reproduction of a real multi-leg
power-electronics reference circuit, actually built and run** (real `maturin develop` in a
scratch venv, not just Rust-level tests). It is kept out of this repo per
`docs/decisions/0002-no-private-content.md` — the reproduction itself lives in the private,
non-public project it was drawn from. It reproduces the hand-written reference netlist's
topology: 2 defs, 6 instances (`X_DQ1..4` of `sw_leg_fixed`, `X_S1`/
`X_S2` of `bidir_sw_fixed`), 27 top-level blocks, 44 wires, def bodies of 6 blocks/10 wires
and 9 blocks/15 wires. Primary H-bridge in the leg-stack convention with hand-specified
positions (same as `h_bridge_3phase.py`), transformer as the E/F dependent-source pair the
reference netlist itself uses, secondary leakage inductance, both bidirectional poles, the full AC
output network, and — the actual proof — one shared `FSW_CONST`/`DUTY_ALL` but a **distinct
phase source per instance**, asserted. **Ran clean on the first real execution**, no engine
gaps hit. Round-trips through real `save_document`/`load_document`.

**Fidelity caveats, flagged rather than glossed**: `source.const`, `source.voltage.dc`,
`passive.resistor`/`.capacitor`/`.inductor`, and the `source.dependent.vcvs`/`.cccs`
transformer pair have no GSF v2 fixtures yet — block `type` is an open pattern-checked
string with no catalogue validation in Phase 1, so these are structurally real but
un-fixtured, and their port ids (`p`/`n`, `p1`/`p2`, `cp`/`cn`) are this example's
convention rather than a catalogued contract. The reference netlist's own `sw_leg_fixed` body
also names its snubber's internal node (`snub`) and `bidir_sw_fixed`'s shared `com` node;
those are expressed here as chained wires between block ports rather than named nets (the
same fan-out convention `h_bridge_3phase.py` established), which is equivalent
connectivity but loses the net *name*. Nothing was silently dropped.

**Verification**: `cargo test --workspace --exclude gsim-py` 60 (gsim-core unit, was 40) +
28 (fixture, unchanged) + 29 (gsim-wasm, was 22) and `cargo test -p gsim-py
--no-default-features` 23 (was 16) = **140 total, up from 106**. `cargo clippy --workspace
--all-targets -- -D warnings` and `cargo fmt --all -- --check` clean. `h_bridge_3phase.py`

**What remains**: netlist compilation is still out of scope, so no `.SUBCKT`/`X`-card text
is ever *emitted* from a `SubcktDef` — that is the deferred compiler phase's job, and the
structured body was chosen specifically so it can be. `hierarchy.subsystem.*` authoring

## 2026-09-04 11:14 — Component-library "stamp" proof case: `examples/h_bridge_3phase.py`

User wants a component-library system for `general-simulator-gui` (KiCad-style, but for
higher-level power-electronics topologies — H-bridge, 3-phase rectifier, snubbered switch,

subschematic support is worth building — user agreed, asked for the 3-phase H-bridge as that
proof case.

port) is exactly how a fan-out net is expressed here. The stamp's boundary manifest names one
canonical `(block, port)` per net rather than requiring a caller to know "any port on this net
works."

## 2026-09-04 10:32 — Real PyO3 bindings in `gsim-py`

Implemented the full JSON-in/JSON-out `gsim-py` surface: `evaluate_component`,
`validate_parameters`, `new_model`, `add_block`, `remove_block`, `set_param`, `add_model_param`,
`connect`, `auto_arrange`, `load_document`, `save_document`, `place_without_overlap`,
`layered_layout`, plus the pre-existing `version`. Every function takes/returns Python `str` (JSON
text) and raises a real `PyErr` (`ValueError`) carrying the underlying Rust error's `Display`
message on failure — no panics, no opaque exceptions.

**Interface design**: deliberately stateless, matching the task's mandate — no `ModelBuilder`
object crosses the FFI boundary. A caller builds a `Model` up incrementally by round-tripping its
JSON through successive calls (`new_model` -> `add_block` -> `connect` -> ... ->
`save_document`), each call internally doing `ModelBuilder::from_model` / `.into_model()`. This
avoids needing GC/lifetime integration for a Rust object living inside Python's object model, and
keeps `gsim-py` a thin wrapper rather than a second place logic could drift into — matching
`gsim-core`'s own "JSON as the interchange format everywhere" philosophy. `crates/gsim-wasm` got
the identical JSON contract from a sibling agent in parallel (not directly coordinated, but the
interface shape was specified identically to both — see the next entry down).

**`gsim-core` gaps filled** (small, additive, not duplicated in `gsim-py`):
- `document::NewBlockSpec` and `document::ConnectOptions` gained `#[derive(Deserialize)]` (with
  per-field `#[serde(default)]` matching each type's existing `Default` semantics) so a binding
  can parse a caller's JSON spec straight into the real builder input type instead of hand-rolling
  an equivalent shadow struct.
- `contract::ValidationFailure` gained `#[derive(Serialize)]` — it previously had no Serialize
  impl at all, which would have forced `gsim-py` to duplicate its two-field shape by hand.
- `layout::Rect` gained `#[derive(Serialize, Deserialize)]` for the same reason (parsing a
  caller's `{"x":..,"y":..,"w":..,"h":..}` JSON array for `place_without_overlap`).

**Error-message design for `connect`/`add_block`/`set_param`/`add_model_param`**: `BuilderError`'s
own `Display` impl phrases some variants descriptively rather than by keyword (e.g.
`CrossParadigm` renders as "cannot connect a PhysicalNetwork block directly to a SignalFlow
block..." with no literal word "cross-paradigm"; `DanglingWire` renders as "wire references
unknown block '...'" with no literal word "dangling"). Since the task explicitly requires a caller
be able to identify *which* `BuilderError` case occurred from the message text alone, added a
`builder_err_to_py` helper (in `gsim-py`, not `gsim-core` — this is presentation, not logic) that
prefixes the real, unmodified `Display` message with a stable keyword
(`duplicate:`/`dangling:`/`cross-paradigm:`/`unknown-block:`/`invalid-block:`) rather than
replacing or summarizing it.

**Build note — `extension-module` vs `cargo test`**: PyO3's `extension-module` feature
deliberately avoids linking against libpython (a real `.so` extension is loaded by a running
Python interpreter, which supplies those symbols at dlopen time), which is exactly what breaks
`cargo test`'s own test binary (linked standalone, no interpreter host). Made `extension-module` a
feature (default-on, so `cargo build`/`maturin` are unaffected) and run `cargo test -p gsim-py
--no-default-features` to get a real libpython-linked test binary; a `pyo3 = { features =
["auto-initialize"] }` dev-dependency lets `#[test]`s call `Python::attach` (0.29's rename of
`with_gil`) to read a `PyErr`'s message without an embedding host.

(`new_model` -> two `add_block`s -> `connect` -> `auto_arrange` -> `save_document` ->
`load_document` round-trip, asserting layout actually moved blocks), plus one error case per
fallible function (dangling wire, cross-paradigm, duplicate block id, invalid rotation, unknown
