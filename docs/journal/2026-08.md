## 2026-08-29 19:02 — Repo scaffolded: naming, scope, and prior-art audit

**Ask:** create a new sibling repo to host a Rust core (+ PyO3/wasm-bindgen bindings) that
`general-simulator-gui`'s frontend and a Python automation library both build on, so the
component-drawing contract, the `.gsim_sch` document format, and (eventually) netlist
compilation exist once instead of drifting across TypeScript and Python implementations.

**Naming, corrected twice before landing:**
- Repo was first scaffolded as `gsf-core`. Discovered mid-scaffold that "GSF" is already a real,
  narrower name in `general-simulator-gui`: `docs/specs/gsim-symbol-format-spec.md` defines
  "GSF — Gsim Symbol Format" as a single-*component* authoring format with a fully-implemented
  Python API (`gsim_model.symbol`) — not the broader thing being designed here. Renamed the repo
  and all three crates to `gsim-core`/`gsim-py`/`gsim-wasm` to match the ecosystem's actual
  prevailing name (`.gsim`, `.gsim_sch`, `gsim_model`, `gsim_loader.py`) instead of introducing a
  second, colliding acronym.
- User proposed reusing "gsim" to mean the per-component format and "gsim_sch" the full
  schematic. Settled on: keep the *existing* file extensions as-is (`.gsim_sym` for one
  component, `.gsim_sch` for a full schematic) and use "gsim"/"GSF" only as project-level/
  conceptual names — not resurrecting the retired bare `.gsim` v1 extension (already superseded
  by `.gsim_sch` v2, "hard cutover, no migration shim" per that repo's own spec) for a third,
  unrelated meaning.

**Prior-art audit** (`packages/gsim-model` in `general-simulator-gui`, read in full before
deciding scope — see the fork/agent report this entry summarizes):
- `ModelBuilder`/`document.py`/`wire.py`/`block.py` already give a real, validated, tested
  `.gsim_sch` construction API (explicit position/rotation/mirror, `connect()` with
  `DanglingWireError`/`DuplicateIdError`, cascading wire cleanup on block removal). Not being
  redone from scratch — `gsim-core` supersedes it, doesn't duplicate ideas it already got right.
- `.gsim_sym`/GSF v1 (component authoring: primitives, transform chaining, `SymbolBuilder`,
  `ComponentDefinition`, `merge_into_catalog()`) is fully implemented and in real production use
  (BJT/MOSFET symbols) — but confirmed, by reading `symbol.py` directly, to bake every primitive
  to fixed coordinates at authoring time only, by explicit design ("no runtime transform
  evaluation is needed"). No parametric ports/geometry exist anywhere in the codebase today.
- **No autolayout exists anywhere.** `gsim_model/layout.py` is pure port-geometry math (port
  centers, a single-bend wire router) despite its name — zero auto-spacing or collision
  avoidance. This is the concrete gap behind "an agent building a schematic in code must be able
  to produce a clean, non-overlapping screenshot," which today is impossible without the caller
  hand-placing every coordinate.
- Netlist compilation is **not** in `gsim_model` — it lives in the much larger
  `packages/simulator/src/simulator/compiler/` pipeline (`ir1_builder`, `ir2_lowering`,
  `spice_netlist_writer`, `dae_system`, `scipy_compiler`, and more), a sibling package
  `gsim_model` merely delegates to.
- Two gaps worth carrying forward deliberately rather than silently inheriting: subsystem/
  hierarchy authoring has zero builder support today despite being in the schema
  (`SubsystemModel` exists, no `add_subsystem_block()`), and `CrossParadigmWireError` is
  referenced in `gsim_model` comments as an existing precedent but is never actually defined
  anywhere in that codebase.

**Scope decision — staged, not one-shot:** given the compiler pipeline is a much larger lift
than the document/component layer, Phase 1 is scoped to exactly three things: the parametric
GSF v2 component-contract schema (ports/geometry/validation via a safe `${{ }}` expression DSL,
evaluated live as a user edits parameters — e.g. a Sum block gaining a port), the `.gsim_sch`
document/builder model (superseding `packages/gsim-model`), and real autolayout. Netlist
compilation is explicitly deferred to a later phase.

**Design decisions carried in from the preceding conversation** (full detail in
`docs/decisions/0001-scope-and-naming.md`):
- Expression DSL surface is YAML-native control blocks (`for_each`/`as`/`index`/`emit`, `when`)
  with inline `${{ }}` expressions — not raw nested JSON-Logic-style operator trees — evaluated
  by a closed-grammar, pure-data interpreter. No `eval` in any language binding, ever: component
  contracts are expected to come from third-party libraries.
- Generated port ids are index-based and stable — never renumbered when a port is added or
  removed.
- Removing a parameter-generated port that has a live wire attached leaves that wire dangling
  with an error marker in the consuming frontend (reusing its existing `problems-store.ts`
  pattern), rather than auto-deleting the wire or blocking the edit.
- Taxonomy: a device's *simulator target* can change its physical model, not just its parameter
  values — e.g. `general-simulator`'s PWL "ideal diode"/"ideal switch" (renamed today from
  "diode"/"mosfet" across `general-simulator`, `general-mna`, `spice-lsp` docs, and
  a private, non-public project experiments, in a separate cross-repo rename task) are distinct
  taxonomy leaves from a real SPICE `semi.diode`/`semi.mosfet.n`, not parameter variants of the
  same leaf.
