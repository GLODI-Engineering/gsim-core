## 2026-08-29 20:10 — Autolayout implemented; all three Phase 1 deliverables done

Third and last Phase 1 deliverable. `src/layout.rs` adds two real capabilities that existed
nowhere in the codebase before this crate (confirmed by audit: `packages/gsim-model`'s own
`layout.py` is pure port-geometry math, not autolayout):

- `place_without_overlap` — grid-snapped nearest non-overlapping position for one new block,
  searching outward along a chosen axis from a desired point. For incremental construction.
- `layered_layout` — a simple longest-path layered (Sugiyama-style) layout driven by wire
  connectivity: blocks flow left-to-right by signal-flow depth (Kahn's algorithm), stacked
  vertically within a layer. Deliberately does not attempt to minimize wire crossings — the
  actual gap being closed is "nothing, or every block stacked at the origin," not "not as pretty
  as a real EDA autorouter." A feedback loop (common — a PID wired around a plant) does not hang
  it: cycle members simply keep whatever layer Kahn's algorithm reached before the cycle blocked
  further progress, an acceptable cosmetic compromise since this is a layout aid, not solver
  input.

`ModelBuilder::auto_arrange(bbox_of, column_gap, row_gap)` wires this into the document/builder
model: gathers block ids/sizes and wire endpoints from the live model, calls `layered_layout`,
writes positions back. Deliberately takes a `bbox_of` closure rather than depending on
`crate::contract` (GSF v2) directly, keeping the document model decoupled from rendering/contract
concerns — the caller (which does have component contracts) supplies sizes.

**Verification**: 48 tests total (40 unit incl. 6 new `layout::*` tests and 1 new
`auto_arrange` integration test in `document::builder`, 8 fixture integration tests unaffected),
`cargo clippy --all-targets -- -D warnings`, `cargo fmt --all -- --check` — all clean, first run.

**Phase 1 is now complete**: GSF v2 (parametric component-contract schema), the `.gsim_sch`
document/builder model, and autolayout are all implemented, tested against real fixtures where
applicable, and committed. Netlist compilation remains explicitly deferred to a later phase per
the original scope decision (`docs/decisions/0001-scope-and-naming.md`). Not yet done, and worth
scoping as the natural next step: wiring `gsim-py`/`gsim-wasm` bindings to actually expose this
surface (currently both still only export the `version()` smoke-test function), and the
integration work of a builder's blocks carrying real GSF v2 contracts end-to-end (today
`document` and `contract` are deliberately separate, connected only by the caller-supplied
`bbox_of` closure).

## 2026-08-29 20:07 — `.gsim_sch` document/builder model implemented

Second of Phase 1's three deliverables done (GSF v2 was the first; autolayout remains).
`src/document/` now has `Block`/`Wire`/`Model`/`GsimSchDocument` (field shapes matching
`docs/specs/gsim-sch-format.md` §3-8 and cross-checked against `packages/gsim-model`'s actual
`block.py`/`wire.py`/`document.py`) and `ModelBuilder`, mirroring `gsim_model`'s real
`ModelBuilder` surface confirmed by the earlier audit: `add_block` with explicit
position/rotation/mirror and auto-id generation, `connect()` validating both endpoints exist,
`remove_block` cascading wire deletion, `set_param`/`add_model_param`.

**One deliberate improvement over `gsim_model`, not just parity**: `connect()` now actually
enforces the cross-paradigm boundary (`docs/specs/gsim-sch-format.md` §8.3 — a `signal` wire and
a `physical-electrical` wire cannot connect directly, only through a `converter.*` block) via a
real `BuilderError::CrossParadigm`, computed from each block's `paradigm` field
(`Paradigm::bridges_paradigms()`: `converter`/`routing`/`hierarchy`/`annotation` blocks bridge;
anything else needs matching paradigms). `gsim_model` only ever *referenced* a
`CrossParadigmWireError` in comments (`subckt.py:79`, `builder.py:196`) without ever defining it
— flagged as a real gap in decision 0001; resolved here rather than carried forward.

**Explicitly out of scope this pass, same boundary `gsim_model` already drew (not new gaps)**:
subsystem/hierarchy block authoring (schema has `SubsystemModel`; no builder method creates one,
matching `gsim_model`'s own gap noted in the audit), `spice-subckt` body parsing (opaque text,
same as `gsim_model`'s `SubcktDef.body`), and `lines`/`nets`/`simulation` (round-tripped as
opaque JSON, matching `gsim_model.Model.simulation`'s own "out of scope" docstring).

**Note on `connect()`'s limits**: it validates the *paradigm* relationship between the two
blocks, not that the caller's asserted port `kind` actually matches either block's real port
definitions — that requires catalogue access (`packages/blocks/**/metadata.yaml`), which this
crate doesn't consume yet. Full §8.1 compatibility-rule enforcement (kind must match, modulo
signal-bus name-matching and `mixed`-port/Goto-From nuances) is deferred until GSF v2 contracts
and `.gsim_sch` documents are wired together — not attempted here to avoid a half-implementation
of a check that needs data this crate doesn't have yet.

**Verification**: 41 tests total (33 unit incl. 8 new `document::*` test modules, 8 fixture
integration tests unaffected), `cargo clippy --all-targets -- -D warnings`,
`cargo fmt --all -- --check` — all clean, first run.

**What remains**: autolayout — the one Phase 1 deliverable not started. `packages/gsim-model`'s
own `layout.py` was confirmed by audit to be pure port-geometry math, not autolayout; there is
nothing to port, this is new work.

## 2026-08-29 19:58 — Real `general-simulator` component fixtures; three variadic-port patterns confirmed

Per the user's request, audited every component `general-simulator` actually supports (forked
research task reading `pwl-devices`, `continuous-blocks`, and `general-mna`'s SPICE-syntax
devices) and authored 8 real GSF v2 fixture files under
`crates/gsim-core/tests/fixtures/general_simulator/`, each proving a distinct structural pattern
found in the audit — not synthetic examples:

- `passive.diode.ideal` / `passive.switch.ideal` — static components, fixed ports, a
  cross-parameter `validate` rule (`v_breakdown < v_th`).
- `control.pid` — simplest static reference case.
- `control.transfer_function` — a variable-*length* array parameter (`num`/`den`) that does
  **not** drive port count, contrasted deliberately with the next three.
- `control.sum` — the real `general-simulator` `sum(inputs, signs)`: `signs` is a numeric ±1
  array, not the char-string toy example from earlier design conversation. Array-length-driven
  port count.
- `control.product` — port count driven by a plain integer parameter via the new `range()`
  builtin, rather than an existing array's length — a second, simpler variant of the same
  pattern.
- `control.state_space` — **matrix-dimension**-driven port count: inputs = width of `b`'s first
  row, outputs = row count of `c`. Structurally different from Sum/Product (dimension of a
  parameter, not its own length).
- `logic.gate` — **enum-selector**-driven arity: `op == "not"` forces exactly one input
  regardless of `n_operands`, using the new `if()` builtin inside a `for_each` source
  (`if(params.op == 'not', range(1), range(params.n_operands))`).

All 8 pass as `tests/general_simulator_fixtures.rs` integration tests.

**Gaps found and fixed while authoring these** (the fixtures immediately exposed real limits the
earlier synthetic Sum example never exercised):

1. **Missing builtins.** No way to synthesize an index range, index into an array/object, or
   pick a `for_each` source conditionally. Added `range(n)`, `at(container, key)`, and a
   short-circuiting `if(cond, then, else)` (special-cased in `eval()`, not `eval_call`, so an
   untaken branch — e.g. an out-of-bounds `at()` — is never evaluated).
2. **`==`/`!=` compared raw `serde_json::Value` equality**, so a caller-supplied integer-backed
   parameter (`5` from external JSON) compared unequal to an expression literal of the same
   value (always `f64`-lexed, `5.0`) — `${{ value == 5 }}` was silently `false` for a perfectly
   valid integer. Fixed with a numeric-aware `values_equal()`. Known remaining gap, not fixed
   (low priority): the same representation mismatch can still bite nested inside array/object
   equality (`params.b == [[1,2],[3,4]]`), which isn't a realistic validation-expression shape
   and wasn't worth the recursive-normalization cost right now.
3. **`evaluate_component`/`validate_parameters` only defaulted a parameter's own missing value**,
   not other parameters referenced cross-param (`v_breakdown`'s `validate` needs `params.v_th`).
   A caller supplying only `v_breakdown` would have hit "unknown field 'v_th'" even though the
   contract declares a default for it. Fixed with `resolved_params()`: build the full
   defaults-then-overrides map once, use it for every evaluation, not just the referenced
   parameter's own fallback.

**Verification**: `cargo test --workspace` (29 total: 21 unit + 8 fixture integration tests),
`cargo clippy --all-targets -- -D warnings`, `cargo fmt --all -- --check` — all clean.

**What remains**: the audit found ~12 more taxonomy entries worth cataloguing eventually
(discrete PID, hysteresis, VCO, PMSM, the 6-member Clarke/Park transform family, 3 math-function
enum components, table lookup, SR latch, flip-flops, complementary-PWM-with-deadtime) — not
authored as fixtures since the 8 above already cover every *structural* pattern GSF v2 needs to
handle; the rest are more of the same shapes. Still not started: the `.gsim_sch` document/builder
model and autolayout (Phase 1 scope, see `README.md`).

## 2026-08-29 19:48 — GSF v2 implemented end to end in `gsim-core`

Implemented the whole GSF v2 pipeline designed in `docs/decisions/0001-scope-and-naming.md`:
`expr` (lexer/parser/AST/evaluator for the closed-grammar `${{ }}` language — arithmetic,
comparison, boolean ops, dotted `var` lookups, and the fixed builtin whitelist `split`, `count`,
`concat`, `max`, `min`, `matches`), `template` (`${{ }}` string interpolation, whole-string
expressions preserve their type instead of stringifying), `resolve` (`for_each`/`as`/`index`/
`emit` and `when` — the mechanism that expands a dynamic `ports:`/`primitives:` list into its
concrete form), `port`/`primitive` (static output shapes, `Primitive` mirroring
`general-simulator-gui`'s `primitive-renderer.ts` union field-for-field), and `contract`
(`ComponentContract`, `Parameter` validation, `evaluate_component` tying it together). 15 unit
tests, all passing; a Sum-block fixture (`signs: "++-"` growing a port and its bbox) exercises
the whole pipeline end to end.

**Bug found and fixed during testing**: `resolve_for_each` initially called the raw expression
evaluator directly on `for_each`'s value instead of going through `Template::parse` first, so it
choked on the `${{ }}` delimiters every real definition actually has around it (`when` handling
already went through `Template::parse` correctly — only `for_each` had the gap). Caught
immediately by the Sum-block test failing with "unexpected character '$'".

**Second bug**: `for_each`'s `index` binding (`Value::from(index as f64)`) printed as `"0.0"`
when interpolated into a port id (`"in${{ i }}"` → `"in0.0"`), because `serde_json::Number`'s
`Display` keeps a trailing `.0` for a float-backed integer value. Fixed by extracting a shared
`fmt::stringify()` (used by both `template`'s interpolation path and `expr::eval`'s `concat()`
builtin, which had the same bug latent but untested) that prints a whole-valued float without
the decimal point.

**Design gap surfaced by testing, not fixed (a real limitation, documented rather than
papered over)**: the "generated port ids are stable, never renumbered" rule in decision 0001
only holds for **append/remove-at-the-end** edits to a bare string parameter like `signs`. A
`for_each` over `split(params.signs, '')` derives each port's id from its *current position* in
that split array — there is no persisted identity for one character independent of its position,
so removing a sign from the *middle* of `signs` does shift every later port's id (see
`contract::tests::a_bare_string_param_only_gives_positional_not_true_identity_stability`, which
demonstrates this deliberately rather than asserting a stability guarantee this contract shape
cannot give). A component that needs genuine stability across interior inserts/removals — not
just growing/shrinking at the end — must use a structured array parameter whose elements each
carry their own `id`, with `emit` referencing `"${{ item.id }}"` instead of an index. Worth
raising with the user before authoring any real component whose UI lets a user splice signs/taps
into the middle of a list, rather than only appending — the frontend interaction design and the
contract shape need to agree on which case is actually supported.

**Verification**: `cargo test --workspace` (15 gsim-core tests, 0 in the still-empty
`gsim-py`/`gsim-wasm` binding crates), `cargo clippy --all-targets -- -D warnings`,
`cargo fmt --all -- --check` — all clean.

**What remains**: the `.gsim_sch` document/builder model and autolayout (neither started yet —
see `README.md`'s Phase 1 scope). Next up: reading every component `general-simulator` supports
and authoring their GSF v2 config files as real-world test fixtures for this crate, per the
user's request.

## 2026-08-29 19:02 — Repo scaffolded: naming, scope, and prior-art audit

**Ask:** create a new sibling repo to host a Rust core (+ PyO3/wasm-bindgen bindings) that
`general-simulator-gui`'s frontend and a Python automation library both build on, so the
component-drawing contract, the `.gsim_sch` document format, and (eventually) netlist
compilation exist once instead of drifting across TypeScript and Python implementations.

**Naming, corrected twice before landing:**
- Repo was first scaffolded as `gsf-core`. Discovered mid-scaffold that "GSF" is already a real,
  narrower name in `general-simulator-gui`: `docs/specs/gsim-symbol-format-spec.md` defines
  "GSF — Gsim Symbol Format" as a single-*component* authoring format with a fully-implemented
  Python API (`gsim_model.symbol`) — not the broader thing being designed here. Renamed the repo
  and all three crates to `gsim-core`/`gsim-py`/`gsim-wasm` to match the ecosystem's actual
  prevailing name (`.gsim`, `.gsim_sch`, `gsim_model`, `gsim_loader.py`) instead of introducing a
  second, colliding acronym.
- User proposed reusing "gsim" to mean the per-component format and "gsim_sch" the full
  schematic. Settled on: keep the *existing* file extensions as-is (`.gsim_sym` for one
  component, `.gsim_sch` for a full schematic) and use "gsim"/"GSF" only as project-level/
  conceptual names — not resurrecting the retired bare `.gsim` v1 extension (already superseded
  by `.gsim_sch` v2, "hard cutover, no migration shim" per that repo's own spec) for a third,
  unrelated meaning.

**Prior-art audit** (`packages/gsim-model` in `general-simulator-gui`, read in full before
deciding scope — see the fork/agent report this entry summarizes):
- `ModelBuilder`/`document.py`/`wire.py`/`block.py` already give a real, validated, tested
  `.gsim_sch` construction API (explicit position/rotation/mirror, `connect()` with
  `DanglingWireError`/`DuplicateIdError`, cascading wire cleanup on block removal). Not being
  redone from scratch — `gsim-core` supersedes it, doesn't duplicate ideas it already got right.
- `.gsim_sym`/GSF v1 (component authoring: primitives, transform chaining, `SymbolBuilder`,
  `ComponentDefinition`, `merge_into_catalog()`) is fully implemented and in real production use
  (BJT/MOSFET symbols) — but confirmed, by reading `symbol.py` directly, to bake every primitive
  to fixed coordinates at authoring time only, by explicit design ("no runtime transform
  evaluation is needed"). No parametric ports/geometry exist anywhere in the codebase today.
- **No autolayout exists anywhere.** `gsim_model/layout.py` is pure port-geometry math (port
  centers, a single-bend wire router) despite its name — zero auto-spacing or collision
  avoidance. This is the concrete gap behind "an agent building a schematic in code must be able
  to produce a clean, non-overlapping screenshot," which today is impossible without the caller
  hand-placing every coordinate.
- Netlist compilation is **not** in `gsim_model` — it lives in the much larger
  `packages/simulator/src/simulator/compiler/` pipeline (`ir1_builder`, `ir2_lowering`,
  `spice_netlist_writer`, `dae_system`, `scipy_compiler`, and more), a sibling package
  `gsim_model` merely delegates to.
- Two gaps worth carrying forward deliberately rather than silently inheriting: subsystem/
  hierarchy authoring has zero builder support today despite being in the schema
  (`SubsystemModel` exists, no `add_subsystem_block()`), and `CrossParadigmWireError` is
  referenced in `gsim_model` comments as an existing precedent but is never actually defined
  anywhere in that codebase.

**Scope decision — staged, not one-shot:** given the compiler pipeline is a much larger lift
than the document/component layer, Phase 1 is scoped to exactly three things: the parametric
GSF v2 component-contract schema (ports/geometry/validation via a safe `${{ }}` expression DSL,
evaluated live as a user edits parameters — e.g. a Sum block gaining a port), the `.gsim_sch`
document/builder model (superseding `packages/gsim-model`), and real autolayout. Netlist
compilation is explicitly deferred to a later phase.

**Design decisions carried in from the preceding conversation** (full detail in
`docs/decisions/0001-scope-and-naming.md`):
- Expression DSL surface is YAML-native control blocks (`for_each`/`as`/`index`/`emit`, `when`)
  with inline `${{ }}` expressions — not raw nested JSON-Logic-style operator trees — evaluated
  by a closed-grammar, pure-data interpreter. No `eval` in any language binding, ever: component
  contracts are expected to come from third-party libraries.
- Generated port ids are index-based and stable — never renumbered when a port is added or
  removed.
- Removing a parameter-generated port that has a live wire attached leaves that wire dangling
  with an error marker in the consuming frontend (reusing its existing `problems-store.ts`
  pattern), rather than auto-deleting the wire or blocking the edit.
- Taxonomy: a device's *simulator target* can change its physical model, not just its parameter
  values — e.g. `general-simulator`'s PWL "ideal diode"/"ideal switch" (renamed today from
  "diode"/"mosfet" across `general-simulator`, `general-mna`, `spice-lsp` docs, and a sibling
  experiments repo, in a separate cross-repo rename task) are distinct
  taxonomy leaves from a real SPICE `semi.diode`/`semi.mosfet.n`, not parameter variants of the
  same leaf.
