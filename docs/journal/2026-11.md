## 2026-11-18 (2) — Two nets could emit under one node name (#30)

The same hole as #28, one layer down, and worse. `nets::resolve_scope` named each net and never
compared the number of nets with the number of names. Three sources share that namespace — a
`.SUBCKT` boundary port, a user's `wire.net`, and the generated `n_<block>_<port>` — and
`sanitize` maps every non-alphanumeric character to `_`, so `V-OUT` and `V_OUT` are one emitted
name. Two roots resolving to one name simply wrote the same string into both of `NetScope`'s maps:
`names: BTreeSet` absorbed the duplicate and every endpoint of both nets reported the same node.

Why it is worse than the element case: there, two devices shared a name and the voltages were
still right, because stamping is positional. Here two *separate nodes* become one node, which is a
short circuit the author never drew, and the numbers that come out are wrong.

Refused now, at the point the names are assigned, with each net identified by its ports — a net
has no id of its own, so there is nothing else a reader can look for on the sheet:

```text
node name 'V_OUT' is claimed by two separate nets -- one reaching C1.p1, R1.p2, the other
reaching C2.p1, R2.p2 -- so they would be emitted as one node and shorted together.
```

`resolve_scope` therefore returns `Result`, and `build_scope`/`heuristic_reference` carry it.

**The one name many nets may share is `0`.** Several independent grounds are all the reference
node, so excluding it is not an exception to the rule — being the reference *is* being the same
node. A test pins that down, next to one pinning the false positive to avoid: a star net has many
endpoints and one root.

**Verification.** The CI gate set, 211 + 3 + 28 + 2 + 1 + 32 tests (4 new), fmt and clippy clean.

## 2026-11-18 — One name per drawn object, and the map back from the netlist (#28)

Found from the far end of the pipeline. Designing the contract between the simulator's output
and the GUI, the first question is identity: an event says `target: "Rload"`, a result column
says `V(n_Rload_p2)`, and the front end holds block ids. Which block is `Rload`?

`CompileOutput` could not say — it carried `netlist` and `notes` — and the front end cannot work
it out either, because `element_name` is **not injective**:

```rust
element_name("load", 'R') == element_name("Rload", 'R') == "Rload"
```

A sheet with both blocks compiled, with `notes: []`, to

```text
Vdc n_Rload_p1 0 10
Rload n_Rload_p1 n_Rload_p2 10
Rload n_Rload_p2 0 20
```

Two elements of one name, and the second resistor's own terminals named after the *other* block,
so reading the netlist by hand misleads too. The solver accepted it (`general-mna` rejected a
duplicate name only for device letters whose name becomes an unknown — filed and fixed there as
GOTCHA-001, 0.5.1) and the voltages were right: 6.667 V, the correct divider. Stamping is
positional and never looks a name up.

What is lost is every reference **by** name: a rating on the device line, a `kind=rule` card's
`target=`, a `kind=measure`, a controlling branch, a `.IC`, the front end's highlight. Each
resolves to one of the two devices, by iteration order, and nobody is told the other exists.

**Both halves are now in `compile::provenance`.** One pass claims a name per document object,
per netlist namespace, refusing a second claimant with both block paths and the reason two
different ids can collide. The same pass records the map it had to build anyway:

```json
{"element": "Rload", "blocks": ["load"], "role": "element"}
{"net": "n_Rbot_p1", "ports": [{"blocks": ["Rload"], "port": "p2"},
                               {"blocks": ["Rbot"], "port": "p1"}]}
```

Names are the **flattened** ones an engine actually reports — `X1.Rin`, not the body-local `Rin`
— including the boundary substitution an `X` card performs on its def's nets, so a net inside an
instance resolves to the parent's own node where it crosses the boundary.

Three cases the check must *not* reject, each pinned by a test: an ideal switch, whose element
card and `kind=` card share one name by design (`general-mna` joins them by name); a composite,
whose expansion emits several cards that are all one drawn block (`ET1_sec`, `FT1_pri`); and two
instances of one `.SUBCKT`, whose bodies hold two blocks of the same body-local name in different
namespaces.

**Verification.** `cargo fmt --check`, `cargo clippy --workspace --exclude gsim-py --all-targets
-D warnings`, `cargo clippy + test -p gsim-py --no-default-features`, `cargo test --workspace
--exclude gsim-py` (207 + 3 + 28 + 2 + 1 + 32), `cargo doc`. Then end to end through a freshly
`maturin develop`-ed `gsim_py`: the colliding sheet is refused with `duplicate-name: ...`, and the
same sheet with distinct names returns the provenance above.

**Found but not done:** net names have the same hole. `resolve_scope` never checks that two
distinct nets got distinct emitted names, and `sanitize` collapses characters (`V-OUT` and
`V_OUT` both become `V_OUT`), so two nodes can merge into one — a short circuit, silently. Filed
separately rather than folded in here, since it belongs in `nets.rs` and changes that function's
signature.

## 2026-11-06 06:10 — Two ways the compiler emitted a name the engine does not have (#1, #2)

Both issues are the same failure class, found from the other end: a schematic that compiled
cleanly into a netlist naming something the engine never registers. One of the two was silent,
which makes it the worse of the pair by a wide margin.

**#1 — `ref_name`'s fallback to the peer block's own name.** `Scope::ref_name` ended with

```rust
.unwrap_or(peer.block.as_str())
```

so a `field=` reference whose wire landed on a peer **input** port — no recorded output name —
rendered as that peer *block's* name. A block name almost always exists, so nothing failed:
the netlist loaded, the engine ran, and it simulated a circuit nobody drew.

Found while drawing a bidirectional switch pole: one gate driver into the first pole's gate,
then gate-to-gate to share the drive. That emitted `ctrl=DS1B` on the second pole — `DS1B` is a
real block — so both poles were controlled by the wrong thing with no diagnostic anywhere. It
was caught by reading the emitted netlist by hand, which is not a review step anyone should
have to perform.

Now `CompileError::RefNotAnOutput`, naming both ends and what to do instead (fan out from the
driver's output, the convention `examples/h_bridge_3phase.py` already establishes). Nothing in
the crate relied on the fallback: 177 unit tests and all ten `examples/` scripts pass and
regenerate byte-identical `.cir` files.

One path it newly rejects is worth recording, because it was *already* broken and this only
makes it visible: a downstream reference to a **subckt instance's** signal output port. Those
blocks carry no `TypeSpec`, so no output name is recorded for them, and the old fallback emitted
the instance's block id while the X card is named `X<id>` — a name that does not exist either.
Giving an X card's signal outputs real names is a design question of its own, left open; it has
no fixture and no example today.

**#2 — a declared `outputs[0]`.** `Outputs::record` let a user-supplied `outputs` parameter name
index 0. Verified against a real engine run rather than inferred:

```text
SRC kind=const value=3
BLK kind=pyblock path=two.py in=SRC outputs=AAA,BBB
G1  kind=gain k=2 in=AAA
```

→ `error: UnknownBlockInput("AAA")`, while the same netlist's CSV header comes out as
`t,SRC,BLK,G1,BBB`. The engine registers a multi-output block's first output under the block's
own card name and reads only `outputs[1..]` from the list, so `AAA` never exists at all. The
doc comment on `Outputs` already stated that rule; the code then let the parameter override it.

Index 0 is now pinned to the card name, and the override is reported through `CompileOutput.notes`
rather than dropped in silence — the user wrote that name expecting to use it, and should be told
which name to use instead.

**Not done, deliberately:** the engine side. `general-mna` ignoring `outputs[0]` without
complaint is the mirror image of this bug, but that repo is a read-only path dependency here
and `general-simulator`'s own `AGENTS.md` requires explicit confirmation before editing it.

**Verification.** `cargo fmt --check`, `cargo clippy --workspace --exclude gsim-py
--all-targets -D warnings`, `cargo clippy + test -p gsim-py --no-default-features`,
`cargo test --workspace --exclude gsim-py` (177 + 28 + 2 + 32), plus all ten `examples/`
scripts re-run through a freshly `maturin develop`-ed binding.

## 2026-11-18 — 0.5.0, and the bindings become publishable at all

`gsim-core 0.4.0` went to crates.io on 2026-11-17 12:17; the two naming fixes merged the
next morning, `8f8a1ea` (#29) and `b1442bb` (#31). A crates.io version is immutable, so
those fixes had no version a dependent could ask for — merged and unreachable. Both are
breaking (`CompileOutput` gained `provenance`; `compile()` can return `DuplicateName` and
`DuplicateNet`), so this is `0.5.0` rather than a patch.

The second half was invisible until the upload was attempted: `gsim-py` and `gsim-wasm`
depended on the compiler as `{ path = "../gsim-core" }` with no version, and `cargo publish`
refuses a path dependency that carries no version. Both have been marked `publish = true`
since they were created and neither could ever have been published. They also had no
`keywords`, `categories` or `readme`, which decides whether anyone finds the resulting page;
all three are set now, `gsim-wasm` pointing at the workspace README so its crates.io page is
not blank.

**Verification.** `cargo fmt --all --check`, `cargo clippy --workspace --all-targets
-D warnings`, `cargo test --workspace --exclude gsim-py` (28 + 2 + 1 + 32), `cargo publish
--dry-run` for each of the three in dependency order.
