## 2026-11-27 — a subcircuit's parameters are stored in three places and bound in none (#111)

Decision [0010](../decisions/0010-who-owns-the-catalogue.md) calls per-instance parameters *"the
one that matters most"* and does not say which layer binds them. Measured against
`general-simulator 0.8.0`: none does. `.param Rv=330` at the top level solves — `0,5,-0.0151515…`,
5 V over 330 Ω — while the same expression inside a `.subckt` whose header declares `Rv=1000` and
whose `X` card says `Rv=100` fails with `error: Evaluate(MissingSymbol("Rv"))`. The evaluator and
the symbol table work; there is no **scope** to put the formal in.

Three layers hold the value and ignore it. Here, `SubcktDef::params` and `SubcktInstance::params`
exist in `document/subckt.rs` and no code under `compile/` reads either — the emitted `.subckt`
card is `name` plus ports and the emitted `X` card is id, connections and def name, so two
instances carrying different parameters compile byte-identically with no note. `spice-lsp` parses
`Subckt::params` and has no consumer anywhere. `general-mna`'s `hierarchy::expand_body` threads a
`port_map` for nodes and nothing for parameters.

**The owner chose the solver**: `general-mna`'s flatten binds the def's defaults, overrides from
the `X` card and resolves brace expressions as it expands
(`GLODI-Engineering/general-mna#63`). Substituting here instead would mean one `.subckt` per
distinct parameter set, or an inlined body per instance — the compiler reimplementing flattening,
which is the duplication 0010 exists to prevent, and a deck in which the two instances no longer
look like two instances.

**What that costs this crate, recorded as a rule in the amendment**: do not emit a parameter whose
binding cannot be shown. A deck carrying `Rv=100` into a solver that drops it parses cleanly and
loses the value one repository further down, which is worse than refusing. So #111 emits formals
and the instance tail only after a `general-simulator` release carries general-mna#63; until then a
per-instance parameter is refused with the instance and the parameter named. The refusal is correct
under either answer and is not blocked on the solver.

Nothing in this crate changed. Verification is the two decks above, re-run today, and the grep that
finds no reader of either `params` field in `compile/`.

## 2026-11-26 — the catalogue declares a real, so it must hand out one (#104)

210 of the library's `number` parameters carried an integer default. `"default": 5` sitting
beside `"type": "number"` in the same object, for a conductance in siemens.

Invisible from this side. Rust reads both `5` and `5.0` into one `f64`, so nothing here could
have noticed, and nothing did — the contradiction was found from the *other* end, in the
documents it produced. `examples/_builder.py` in the editor repository reads
`gsim_py.catalog()` with Python's `json`, where `5` is an `int` and `5.0` is a `float`, takes
`fidelities[0].params[].default` as each example's starting value, and wrote `"g_on": 5` and
`"IC": 0` into all five committed sheets. The declaration said real, the file said integer,
and a Python reader of the file had no way back.

**The fix is the data, and the guard is what makes it stay fixed.** `serde_json::Number` keeps
the two apart in a parsed value — `is_f64()` against `is_i64()/is_u64()` — so
`a_numeric_default_is_written_in_the_form_its_type_declares` can ask the embedded library
rather than scan the file's text, and it fails loudly on a hand-edit that reintroduces one. It
was watched failing on all 210 first.

**What the module now says, because nothing said it.** `number` and `integer` read as a choice
of input widget, and in a front end that is all they were. They are a statement about the
value, and the only place a writer of a `.gsim_sch` can get it: the trailing zero is not part
of the double, so by the time any of the three writers holds `48.0` it is already `48` and no
amount of looking at it will say what the author meant. That is
GLODI-Engineering/omni-schematics#268, which settled that this catalogue is the declaration;
this is the half that had to be true before anything could format from it.

**Left undeclared on purpose.** `vector` and `matrix` name the container, not the element, so
they say nothing about the numbers inside one — a state matrix is real, but the type does not
say so, and declaring it would need a new field no consumer has asked for. 13 parameters on 5
components. A writer leaves them exactly as they arrived, which is the weakest true statement
available and the right one until something needs more.

## 2026-11-26 — the loader reads its own format (#94)

`.gsim_sch` §5.2 says "the loader evaluates expression strings against the resolved `params`
table". This crate is that loader and it did neither: `{Rload * 2}` went into the deck as
`{Rload * 2}`, and the solver answered `unexpected extra parameter '*'`. A user who typed that
in the inspector, watched its resolved-value readout say `14`, and pressed Run was told that `*`
is an unexpected extra parameter.

Taken as #94's **first** option — evaluate — rather than its second, refuse. The second was a
legitimate stopping point when the issue was filed and is not one now: #100's build feature
refuses a define whose parameter cannot be derived, and a parameter holding an expression was
being counted as underivable *because the loader could not read it*. A refusal that exists only
because of a gap in the reader is not the refusal that feature was written for.

**Two properties, and the second is the one that could have gone badly.** The deck carries the
number, and the document still carries the expression. `save_document` is a parse followed by a
serialize (#78/#79), so substituting at *load* time would substitute in the saved file: a sheet
written with `"R": "{Rload * 2}"` would come back `"R": 14`, and the parameterisation that makes
one sheet serve a sweep would be gone because the user opened and saved their own file. So
resolution lives on the compile path and compiles a substituted **clone**;
`a_round_trip_still_carries_the_expression_the_user_wrote` is what stops a later reader
"simplifying" it onto the loader.

**A separate grammar, and not for the reason the issue gave.** #94 already recorded that §5.2
and `crate::expr` differ in vocabulary — §5.2 has `**` and `sin`/`cos`/`log10`, `expr` has `%`,
comparisons, `at()` — so sharing would accept what the spec forbids and reject what it requires.
True, and not the decisive part. The decisive part is that **the two disagree about what a
number is**: `expr`'s lexer takes digits and dots, so `1.5e-6` is four tokens — `1.5`, the
identifier `e`, `-`, `6` — and `e` is a §5.2 *constant*. Every value on a power-electronics sheet
is written that way, so a shared lexer would not have been an edge case; it would have been
arithmetic on Euler's number, quietly, on the common case.
`a_value_in_scientific_notation_is_one_number_not_four` is the whole justification in one test.

Python's precedence where it bites: `-2**2` is `-4`, `**` is right-associative, `2**-1` parses.
Getting any of those backwards is a different number, not an error.

`substitute` establishes one invariant worth stating because everything downstream rests on it:
**after it, no §5.1 reference and no §5.2 expression remains anywhere in the model** — the table
itself included. So element cards, `ic`, analysis directives and #100's `-D` bindings all read a
value without knowing §5.2 exists, and `code_build` needed no change at all.

**Cycles** are a named error with the loop in the message (`A -> B -> A`), not a fixed-point loop
that stops making progress. A user shown the stuck set has to work out which edge to cut; a user
shown the loop does not. Self-reference counts.

**The refusal that would have made this unusable**, so it has its own test: a bare identifier
that names no declared parameter is left alone. `ts=variable`, a `kind=` variant, an output name
and `./ctrl.so` are all written that way, and treating them as unresolved references would have
refused almost every sheet on the way to fixing #94.

**Three of #100's tests flipped**, which is the honest signal rather than an obstacle: the ones
asserting that an expression-valued parameter is underivable. `docs/decisions/0009` §8 is amended
with why — the record predicted this in as many words — and `optional`'s scope narrowed with it.

**Watched failing, three ways.** Substitution removed, which is the pre-#94 behaviour: 6 of 12
red, and the 6 still green are the ones that call `resolve_table`/`substitute` directly, which is
correct. `crate::expr`'s number rule put back (no exponent): the scientific-notation test alone.
Cycle detection replaced by a silent `break`: both cycle tests.

**The resolved table comes back** in `CompileOutput::params`, through both bindings, for the
reason `Provenance` does: a front end that computes a resolved value is a second implementation
of §5.2, and that is how the inspector came to show a confident `14` beside a field that could
not compile. `omni-schematics#199` closes on that, but **not yet** — the editor reads this
through its committed WebAssembly bundle, and `check-gsim-wasm-fresh.mjs --against-engine`
requires the bundle's provenance commit to be the engine's default-branch HEAD. So the parity
flip and the deletion of `params/param_expression.ts` wait on this merging, not on more work.

**Verification.** `cargo fmt --all --check`, `cargo clippy --workspace --exclude gsim-py
--all-targets -D warnings`, `cargo clippy + test -p gsim-py --no-default-features`,
`cargo test --workspace --exclude gsim-py` (252 + 38 + 12 + the rest, 0 failed), `cargo doc
--workspace --no-deps` with no new warning.

## 2026-11-26 — and the constants `-D` cannot carry (#98, #100)

The owner read the three options and decided: `-D` on the compile line for scalars, a generated
`.h` for a lookup table, an array or a struct initialiser. His `.c` is never rewritten, so
`omni-schematics#237`'s clickable diagnostics and `clangd` both keep working — which was the
whole case against substituting into the source.

"Automatically", which is what he asked of the include, is a **forced include**: `-include` for
clang and gcc, `/FI` for MSVC. The header is in scope without the user writing a line, and the
file they opened is still the file the compiler read. Making them write the `#include` is
rejected as a default because it is a line to remember in every block, and forgetting it fails
as an undefined identifier rather than as a sentence.

**The implementation worth describing is the thing that is not there: a second code path.** The
owner's third requirement was that both transports refuse identically, so that an author's
choice of shape cannot change how safe their build is. That is not met by writing the check
twice — it is met by `defines` saying nothing at all about transport and the *shape of the
resolved value* deciding. `carry()` is four lines: a number, a bool or a string becomes
`Carried::Scalar`, an array becomes `Carried::Structured`, anything else refuses. One list, one
pass, one set of refusals, and the author never picked a transport, so there is no laxer path to
find.

The header's path is **derived from the artifact**, not declared — `runs/case3/ctrl` gives
`runs/case3/ctrl_gsim_constants.h`, and a `lib` already carrying `.so`/`.dylib`/`.dll` gives the
same name rather than `ctrl.so_gsim_constants.h`. Same reason a step has no `output` field (0009
§4): a second place to write a path is a second place for it to drift. It also makes requirement
1 structural rather than a rule to remember — the header cannot land in the user's `code/`
folder, because it is named after the artifact and the artifact is not there.

A nested array nests: `[[1,2],[3,4]]` becomes `{ { 1, 2 }, { 3, 4 } }`, which is what a 2-D
table and a struct initialiser both want. An object or a `null` anywhere inside has no C
spelling and refuses, naming the value.

**Watched failing, twice.** An array stringified onto the compile line like any other value —
which is what a careless implementation does, and what `fmt::stringify` would happily produce:
4 red. The header written beside the *source* instead of the artifact, which is requirement 1
violated: exactly the 2 path tests red.

**Still owed on the editor side**, and filed rather than assumed: the forced-include flag
(`-include` / `/FI` is a statement about a compiler, so it is not here), writing the file,
gitignoring it, and comparing it by content rather than mtime — it is rewritten every run, so a
timestamp check would be vacuous and a changed table would be an invisible staleness. §6's
record already carries the lines verbatim, so the comparison is the equality test that already
exists.

**One format cost, paid here rather than discovered later.** `.gsim_sch` §5.1's `ParamValue` is
a number, a boolean or a string, so a sheet could not declare a table at all. `ModelParam::value`
is a `serde_json::Value` and already parsed one; the editor's own JSON Schema did not, and that
is the half that had to change.

## 2026-11-26 — the define, resolved and refused (#100)

0009's schema and its enforcement, in one change rather than two: a format a sheet can write
and nothing checks is a format that produces a block whose constants disagree with its circuit,
which is the window the record was written to close.

`Model::code_build` holds the plan, `Block::source` holds the file the user edits — this crate's
half of `omni-schematics#222`, which until now was four candidate paths the editor had to tell
the user it was guessing at — and `Block::build` names the step. All three are optional and
`skip_serializing_if`, so a sheet written before today saves byte for byte and compiles byte for
byte, with a test for each.

`CompileOutput::code_build` is the resolved build, and it comes out of `compile_with` **before**
emission. Not for tidiness: resolving after emission would still refuse, but it would refuse
holding a netlist, and the next person to touch it would be one `if` away from returning it.
A define's value goes through `crate::fmt::stringify`, the same function that prints it onto the
element card — which is the one thing that makes "the `-D` and the card carry the same number"
true by construction rather than by review, and the reason this is not the editor's job.

**`kind` is a `String`, not an enum**, and that is 0009 §10 in one line. A step kind this version
cannot build has to be *kept* by the document — a serde enum would fail at parse, so opening a
sheet in an older reader and saving it would delete the user's build — and *refused* by the
compiler, because skipping it leaves an artifact nobody built, which runs. Round-tripping is a
separate obligation from understanding (0008), and the two are now discharged in two different
modules: `document::code_build` judges nothing, `compile::code_build` judges everything.

Nineteen refusals, each with a message that names what the record's table says it names — and
the first of them lists the parameters the sheet *does* declare, which turns a misspelt `from`
into a one-line fix rather than a dead end. Two were added to §8 while implementing: a define
name that is not an identifier, and a `literal` that is an array or an object. Neither is
exotic; both would have reached a compile line as something nobody meant.

**Watched failing first, in three passes.** Resolution stubbed to `Ok(None)`: 27 of 30 red, and
the three that stayed green are the round-trip and pre-feature tests, which is correct. An
absent parameter silently omitting its define — the exact convenience 0009 §9 forbids: the
refusal test red, its **control** (the same sheet with the parameter present) still green, which
is what stops the refusal test from passing against an implementation that refuses everything.
An unknown step kind `continue`d past, and a dotted `from` read as a plain name: exactly those
two red.

Carried through both bindings rather than left in Rust, because the editor compiles through
`gsim-wasm` and would otherwise have to resolve the bindings itself — the thing this whole design
exists to prevent. `gsim-py` gains `underivable-define:` and `bad-code-build:` keywords.

**Needs a release**, and a minor one: `CompileOutput`, `NewBlock` and `NewBlockSpec` each gained
fields and `CompileError` gained two variants, so every struct-literal caller breaks. Not tagged
here.

**Verification.** `cargo fmt --all --check`, `cargo clippy --workspace --exclude gsim-py
--all-targets -D warnings`, `cargo clippy + test -p gsim-py --no-default-features`,
`cargo test --workspace --exclude gsim-py` (236 + 30 + the rest, 0 failed).

## 2026-11-26 — a sheet says how its code blocks are built, as [`0009`](../decisions/0009-a-document-carried-build-for-code-blocks.md) (#98)

The owner chose the document-carried build description over the quicker alternative — the
extension running a build command he configures — and said why: consistency. That reverses the
first of three decisions recorded on `omni-schematics#253`, and the record says so rather than
leaving a reader to find two documents disagreeing.

**What the record is actually about.** Not where to put the flags. A C block is rebuilt per
operating point with `-D` defines derived from the same parameter dictionary that generates the
netlist, so a build that omits one produces a block whose constants disagree with its circuit —
and the run then reports a confident wrong answer, which is `omni-schematics#235` again, caused
by the feature meant to end it. The asymmetry decides the design: a failed build costs a minute,
a wrong constant can survive a study.

So a define is a **binding**, never a value a second place holds. `{ "name": "L_F", "from":
"L_f" }` reads `model.params`; `{ "name": "N_PHASES", "literal": 3 }` is the author saying this
one is not a circuit quantity; there is no third spelling. And the resolved build is a field of
`CompileOutput`, beside the netlist, from the same call and the same parameter read — so when a
define cannot be derived, `compile()` returns `Err` and **there is no netlist either**. The
refusal is not a build step declining to run; it is the deck failing to exist.

Two things found while writing it, each of which killed a simpler design:

- **Nothing can go on the card.** `general-mna`'s `build_kind` ends with `fields.unread()`, and
  an unknown `key=value` on a `kind=cscript` line is a hard error with a test named for it — the
  comment there says the escape hatches are deliberately not exempt. The gate lives in a
  read-only path dependency. So the description never touches the netlist, which is also what
  `general-simulator`'s `--capabilities` has been saying from the other side: `cscript=load-only`.
- **Build-time refusal is not enough.** It says nothing about the artifact already on disk,
  built last week or at another sweep point, which is exactly the artifact a run picks up. Hence
  a build record beside the artifact, carrying the resolved defines *themselves* rather than a
  digest of them: a digest says something is wrong, the list says `L_F was built as 2.8e-06, the
  circuit now says 3.2e-06`. It also costs this crate no dependency.

**Against 0008.** "Preserve, do not interpret" was weighed and rejected for the binding, on the
one thing that cannot be split: the `-D` and the netlist card must carry the same number, and
resolved in the editor that rests on a second implementation of `fmt::stringify` maintained by
hand. The compiler, the flag spellings and the platform suffix stay uninterpreted here, where
`omni-schematics`' `toolchain-probe.ts` already owns them.

**No code with the record**, per the development cycle. `Block::source` (this crate's half of
`omni-schematics#222`), the `code_build` schema, and the resolution with its refusals are filed
as their own issues in milestone 5.

## 2026-11-26 — the engine-side data the editor was waiting on (#64, #83, #85, #77, #61)

Five pieces of one ask: close the engine-side data gaps that block editor features, starting
with the one keeping `omni-schematics`' only red test red.

**`port_sigs` on every signal port (#64).** The editor's FE-65 dimension overlay had never once
rendered in the application, and the reason was here: 4 of 53 signal-domain components carried a
port signature, and the overlay needs one on every block along a path. Reproduced first by
driving the real app — `getByTestId('canvas-dim-overlay')` → "element(s) not found" — then
re-run with this branch's catalogue regenerated into the editor, where the same three insertions
(`source.const`, `control.gain`, `signal_flow.sink.scope`, reached through the aliases) label
both wires `[1]`.

44 components gained a signature, five deliberately did not, and the rule taken was *the
weakest true statement*: a source's output is `[1]` because `kind=const value=<f64>` reads one
scalar; a pass-through says `in: inherit`, `out: from(in)` because that stays true at any width.
`[1]` on everything would also have been true today and was rejected, because
`TypeSpec::vector_output` means this engine does have a vector signal — a state-space block's
output is `rows(c)` wide, so a gain fed from one carries a vector. Those two state-space
components are among the five left blank: the signature language has `shape(<param>)`, which is
a matrix's `[rows, cols]`, and no way to say "that matrix's rows". The other three are the two
boundary ports, whose domain is a parameter's value, and `routing.from`, whose width comes from
another block entirely.

**Two pairs of labels, and a lookup table with the smallest box in the catalogue (#83).** Found
by the editor's real-VS-Code sweep clicking all 68 entries. `Step`/`Step` and `Scope`/`Scope`
are one component twice — the engine's name and the GSF v2 spelling — and `compile::spec` says
so beside both, so the legacy entries now say `(legacy spelling)` and their tooltips say which
one to place. `math.table_lookup` went from `[60, 40]` to `[80, 60]`, ports re-centred, after
measuring that every tier port in the file carrying an offset carries its component's.

**A component resolves under the name a front end places it by (#85).** Found while deciding
which spelling of the scope was canonical. `insert.ts` builds a block with `type: metadata.name`,
and the only two components whose `name` differs from their `id` had that spelling in none of the
three fields `find_component` matches, so placing either from the palette left a block that
failed at Run:

```text
signal_flow.sink.scope  FAIL unknown-type: block 'x1' has type 'signal_flow.sink.scope'
```

`every_component_resolves_under_its_own_id` had asked the same question one field across since
#27. A front end does not place by `id`.

**A wire into a signal port is a block reference, whatever the wire says (#77).** #80's mirror
image. §8.4 makes `wire.kind` a duplicate of the endpoints' port kind so schema validation needs
no catalogue, and `buck_state_space_pi` spells its gate-drive wire `physical-electrical` onto a
pin the library declares `signal` — so a net was invented for a causal reference. Harmless in
that example, because an ideal switch's gate travels as `ctrl=GATE`; draw a gate resistor on the
same net and `Rg n_DSW_g 0 10` appears, on a node nothing drives, which `general-mna`'s own
`Sig2Phys` doc says KCL solves to a silently wrong `0`. Net membership now asks
`library::port_domain` as well as the wire.

Two constructs this grammar cannot express are reported on #77 rather than worked around: a
`sig2phys` output wired into a real node, and a `phys2sig` that has no input port and so reads
its measurement point as a hand-typed net name.

**Subsystems and buses (#61), as [`0008`](../decisions/0008-subsystems-and-buses.md).** The
design question, answered rather than decided unilaterally. "Preserve, do not interpret" — what
#78/#79 established — is permanent for a `.SUBCKT`'s SPICE body and for an unrecognised key, and
is *not* a resting place for a virtual subsystem: `omni-schematics` 0.9.0 deleted the Python that
used to flatten and omni#112 was closed `not_planned`, so today nothing flattens a subsystem
anywhere and Ctrl+G produces a document that fails with `UnknownType`. Buses stay out until a
bus *type* exists.

## 2026-11-21 — a switch is not passive (#60)

`passive.switch.ideal` declares `node_ports` `["d", "s"]`, a block-driven `ctrl` mapped to a
third terminal `g`, a `v_gs_th` gate threshold, and an intrinsic body diode with its own
`body_v_f`, `body_v_breakdown`, `body_g_on` and `body_g_off`. A three-terminal gate-driven
active device with a body diode, filed next to the resistor. `passive.diode.ideal` is passive
in the energy sense but is not a lumped R/L/C element, which is the only thing `passive.` ever
described.

Both are now `ideal.diode` and `ideal.switch`, and `passive.` holds exactly the six lumped
elements: resistor, capacitor, inductor, `inductor.coupled`, transformer, `mutual_inductor`.

**Why not `semi.diode.ideal`, which is the obvious name.** Decision 0001 says a component
targeting general-simulator's ideal diode/switch must be a *distinct catalog leaf* from
`semi.diode`/`semi.mosfet.n`, "not a parameter variant", because folding both into one entry
silently conflates two physical models. `semi.diode.ideal` reads as exactly that variant — leaf
qualifiers are how parameter variants are spelled everywhere else in this taxonomy, so the leaf
cannot carry "different model" no matter what word goes there. The distinction has to live in
the group. 0001 is amended to say so, since its own wording is what ruled out the fix that
looked obvious.

**The rename is provably only a rename.** The leaf words the engine sees are untouched — the
netlist still says `kind=ideal_switch`. Rather than assert that, every example in `examples/`
was run: all ten execute, and the four that name a renamed type emit a netlist byte-identical
to its committed `.cir`. Worth knowing separately: **no CI job runs the examples**, so they
could have rotted silently either way.

**The suite stayed green through the rename, and that is the finding.** Not one test named
either component. A repo whose whole purpose is to be the shared source of these names had
nothing pinning two of them, so a rename that dropped an entry, or left a dangling alias
answering for a deleted model, would have passed. `tests/the_ideal_devices_are_not_passive.rs`
now pins six things, and each was watched fail first:

| forced condition | which guard caught it |
| --- | --- |
| `passive.switch.voltage` put back as an alias | `a_voltage_controlled_switch_is_unknown…` |
| the old id dropped from the aliases | `a_sheet_saved_under_the_old_names_still_opens` |
| the switch left tagged `passive`, grouped `semiconductor` | `the_ideal_family_is_its_own_palette_group` |

Each time exactly one test failed, which is what makes them guards rather than a sweep that
happens to be red.

**Two of this issue's six boxes were already closed by #62** and are now pinned rather than
redone: the transformer and the mutual inductor resolve under one spelling each (the library
had a hyphen, the registry an underscore, and neither half worked), and
`passive.switch.voltage` had already stopped being an alias. The hyphen spellings of both
magnetics were *not* in the aliases though, and a sheet saved before #62 names them, so they
were added and pinned too.

**The new group is a breaking change for the editor, and I nearly missed how.** A new
`category` is not just a word in a JSON file: omni's palette renders
`CATEGORY_ORDER.map(...)` and filters entries by `entry.category === category`, so a category
not in that list renders in **no section at all**. `ideal` is not in it. Both components would
have vanished from the palette while every test in both repos stayed green — nothing on either
side asserts that a catalogue category has a section to appear in. Filed as the editor's half
with that guard as the point of it, not the two-line list edit.

Found by reading `LibraryActivity.tsx` rather than by anything failing. The same read cleared a
suspicion: `routing.from` and `routing.goto` have no `category` at all, which looks like the
same bug, but routing entries are rendered by a separate section keyed on
`paradigm === "routing"`, so they are fine. Worth recording that the null category is harmless
*there* and would not be anywhere else.

## 2026-11-20 11:08 — the compiler ignored its own library's aliases

Found by doing the thing rather than reasoning about it. Before wiring the WASM binding into the
editor I compiled this project's own `.gsim_sch` fixtures through it from Node, to see the path
work end to end. **Every one failed**, on type names:

```
Error: block 'vin' has type 'physical-electrical.source.voltage_dc',
which no netlist emitter knows -- add a TypeSpec for it in compile::spec::REGISTRY
```

`compile::library::find_component` resolves a name through the library's aliases, and its doc
comment states its purpose exactly: *"Documents already on disk name components the way the front
end's catalogue did... Those older spellings are kept as aliases, and this is what makes a saved
sheet still resolve."*

It had **no callers.** So it made nothing resolve. `spec::lookup` was exact-match on
`type_name`, and one crate gave two answers about one name: `data/component-library.json` saying
`physical-electrical.source.voltage_dc` is a compilable DC source, the compiler saying
`unknown-type`. The editor only gets away with it because its own loader canonicalises types on
deserialize — a document written by hand, or saved before that canonicalisation existed, did not
compile at all.

`lookup` now falls back to the library. **The first version of the fix was wrong in an
instructive way**: I wrote `component.r#type.unwrap_or(&component.id)`, reading `type` as the
canonical name. It is the other way round — `id` is the engine's name, `r#type` is the *legacy*
catalogue spelling — so every alias resolved to another name the registry does not have and the
fixtures failed identically. The probe that caught it printed `find_component` and `lookup` side
by side for four spellings, which made the inversion obvious in one line. The test now asserts
both fields explicitly, because the field names actively mislead.

Rebuilt the WASM and ran the fixture again: the type errors are gone and it now fails on
`port 'sw.d' needs a node but no physical-network wire reaches it` — a different layer. That is
the *port*-name translation `omni-schematics`'
`gsim_py_netlist._GSIM_CORE_PORT_NAMES` performs by hand (`routing.ground`'s `gnd` → `p`), and
the same question applies to it: if the library knows a port's older spelling, the compiler
should too. Filed rather than fixed here.

Three other things learned from the same exercise, for whoever wires this up:

- `loadDocument` returns `{schema_version, model}` and `compile` takes the bare `model`, so
  `compile(loadDocument(x))` does not compose. Worth reconsidering.
- `grid: i64` crosses `wasm-bindgen` as a **BigInt**: `newModel("m", "M", 10)` throws
  `Cannot convert 10 to a BigInt`. It must be `10n`.
- `gsim-core` is a **public** GitHub repository, so the editor's CI can check it out and build
  the WASM package with `wasm-pack` — no npm account, no crates.io release, no committed binary.
  That is the difference from `gsim-tools`, which is private and is why the Python compile path
  cannot run in CI at all.


## 2026-11-20 10:57 — the WASM binding can ask what the engine supports

Two functions, and the reason they were missing is the interesting part.

`gsim-py` and `gsim-wasm` are two bindings of one library, and they are meant to expose the same
surface. They did not. Comparing them properly — `dir(gsim_py)` against the built
`gsim_wasm.d.ts`, not against a grep of `js_name` attributes, which misses every plain
`#[wasm_bindgen]` export — the gap was exactly `capabilities` and `catalog`.

Which is the pair that matters most for a browser-hosted editor. It could compile a document and
could not ask what was compilable. So `omni-schematics` is handed a generated
`engine-capabilities.json`, committed to its own repository with an `engine-catalogue-drift` CI
job to notice when it goes stale — a copy with an alarm on it. These two calls are what make the
copy unnecessary.

Both are one-liners over `capabilities_json()` and `catalog_json()`, infallible, so they follow
`version()`'s shape rather than the `Result<String, JsValue>` pattern. The manifest now also
carries `universal_types` from yesterday's #54, which is what a palette needs in order *not* to
filter out the components the editor owns.

**The drift test I wrote first was theatre and I nearly kept it.** It compared two hand-written
lists of function names — both typed by the same hand in the same minute, so it passed by
construction and could never fail. The same trap as asserting that a tolerant emitter drops a
block it was never handed, which caught me yesterday on #54.

The replacement references every function instead: `let _: fn(&str, &str) -> Result<String,
JsValue> = add_block;` and so on. A missing, renamed or reshaped function is then a compile
error, not a silent pass. Checked by renaming `catalog` to `catalogue` and watching the build
fail with `cannot find function 'catalog' in this scope`. The reference list is still
`dir(gsim_py)` copied by hand — a `cfg(test)` build cannot introspect a PyO3 module — so keeping
it in step remains a human job; what changed is that forgetting is now loud on this side.

Next: wiring this into the editor, which is the whole point. The route was chosen over an IPC
`compile` verb because the Python compile path runs
`omni → gsim_tools → gsim_py → gsim-core`, and `gsim-tools` is a **private sibling repository**
that no CI checkout can resolve (the editor's own `pyproject.toml` records why, verified against
uv 0.13). WASM reaches the same compiler with no private dependency, in the same process as the
canvas, and works in the existing e2e harness, which has no kernel at all — its CI job installs
Node, pnpm and Chromium and no Python.


## 2026-11-20 10:40 — the components the editor owns

[#54](https://github.com/GLODI-Engineering/gsim-core/issues/54), and
[decision 0006](../decisions/0006-the-components-the-editor-owns.md).

The owner's framing: some components belong to no library — they are the schematic's own
vocabulary, the editor owns them, and **any** compiler that compiles an Omni Schematics document
must therefore support them. Goto/From are the clear case: a `routing.goto` is not a part anyone
could buy, it is a way of saying *this signal continues over there*, and it means the same thing
whatever engine a sheet is bound for. So are a ground, a wire junction, a scope and a `.SUBCKT`
boundary.

Mostly this crate already met that. Goto/From resolution has been shared since it landed —
`build_scope` calls `routing::resolve_scope` per scope, and the redirect table is in the
`CompileContext` before any `emit` runs. **The gap was the skip.** `general_simulator.rs`
checked `spec.structural` in two places of its own, so a target *happened* to support the
universal components because the only target remembered to. A second one would have had to
remember in its own two places, with nothing to tell its author: a Goto's spec declares no
device letter and no `kind=` name, so emitting one writes a malformed card rather than raising
an error.

Now the concept has a name (`spec::is_universal`, `spec::universal_types()`, both derived from
`TypeSpec::structural` so the list cannot fall behind the registry), the shared pipeline hands
`emit` only `Scope::emittable()`, and the two `if spec.structural { continue; }` sites are gone
because there is nothing left for them to skip.

**The first version of the test proved nothing, and finding that out was the useful part.** It
compiled the sheet for `general-simulator` and asserted no universal component appeared in the
netlist. It passed. It also passed with the filtering reverted — because that emitter is
*tolerant*: a `routing.ground` has no device letter and no `kind=` name, so handing it one
produces no card rather than a bad one. An output assertion against the one target that already
knows the rule cannot test a guarantee about targets that do not.

So the test now defines its own `NaiveTarget` — emits one line per block, filters nothing — as
the stand-in for the second target this crate does not have. `compile_with` was factored out of
`compile` so a target can be written and tested outside `target_for`'s match. Breaking
`emittable()` to leak everything now fails that test by name, which is what I checked before
believing it.

`capabilities()` grew `universal_types` (schema_version 2 → 3), carried separately from `types`
because the question a front end needs answered is not how this engine spells one — none of them
do — but whether it may always offer the component. It may: no engine's catalogue gets to
withhold something the editor owns, and a palette that filters on engine support must not filter
these out.

Also corrected an error of mine in `omni-schematics#112`, which claimed this crate "exposes no
goto/from resolution at all". What I had checked was `dir(gsim_py)`, which lists no
`resolve_goto` — an API surface, not an absence of behaviour. Resolution is not a separate step;
it happens inside `compile()`, which is the whole reason it already applies to every target.

Left open and recorded in the decision: `gsim_sch_flatten` may belong here, and §10.1's
`local`/`scoped`/`global` Goto visibilities still resolve identically because this crate's
`Block` has no parent. Both wait on subsystem hierarchy.


## 2026-11-19 03:08 — PWL, EXP and SFFM can be drawn, and a current source is no longer DC-only

[#7](https://github.com/GLODI-Engineering/gsim-core/issues/7). `general-mna`'s grammar accepts
`DC`, `SIN`, `PULSE`, `PWL`, `EXP` and `SFFM`, and `transient_source.rs` implements every one.
The registry had types for DC, SIN and PULSE on `V` only — so three shapes the engine can solve
could not be drawn at all, and two that existed for voltage had no current counterpart even
though `I` takes the same time functions.

Eight new types, three new `ElementTail` variants (`Exp`, `Sffm`, `Pwl`) and their capability
arms, with parameter names taken from the catalogue throughout — which is why the current
sources' levels are `I1`/`I2` while the voltage sources' are `V1`/`V2`.

**PWL took the interesting decision.** The catalogue declares `points` as a *string* of
space-separated pairs, `"0 0 1u 1 2u 0"` — already the token sequence the card needs, SPICE
suffixes included. A programmatic caller would naturally write `[[t, v], ...]`. Both are
accepted and normalised to one token list, the same answer `control.sum`'s `signs` got earlier
today and for the same reason: the authoring spelling belongs to the catalogue, not to the
emitter. An odd token count is refused rather than truncated — a PWL whose last point was
silently dropped is a different waveform that still simulates.

`TAU1`/`TAU2` hard-fail when missing rather than defaulting to zero. `general-mna`'s evaluator
clamps a zero time constant with `max(f64::EPSILON)`, so an omitted tau would produce a step
instead of an exponential: a different shape, silently.

Verified through the engine, not only in the emitter:

| deck | measured | expected |
| --- | --- | --- |
| `PWL(0 0 1m 5 2m 0)` | 2.5 V at 0.5 ms, 5 V at 1 ms, 0 V from 2 ms | the points, interpolated |
| `EXP(0 5 0 1m 1e30 1m)` | 3.1606 V at t = 1 ms | $5(1 - e^{-1}) = 3.1606$ |
| `SFFM(0 1 1000 2 100)` | oscillating within ±1 | carrier at 1 kHz, modulated |

The EXP row is a hand check rather than a recorded number: at one time constant the rise is
exactly $1 - 1/e$ of the span.

Three emitter tests cover the string spelling, the list spelling and the refused odd count.
`every_compilable_component_compiles_at_every_tier_it_offers` exercises all eight new types from
their own catalogue defaults, which is how the string-versus-array question surfaced: it failed
with "missing required parameter 'points'" until the renderer accepted the catalogue's own
spelling.

Still open on the issue: nothing. `AM`, `noise`, `random` and `rf_port` remain uncompilable, and
that is correct rather than pending — the engine has no such source, so a type here would
promise what nothing can run.

Verification: fmt; clippy and tests as CI runs them (216 + 32 + 28 + 3 + 2 + the tier sweep);
three decks through the engine.

dropping `clamp_lo` from the tier: *"control.pid @ ideal: emitter requires 'clamp_lo', tier offers
[kp, ki, kd, n, clamp_hi]"*. Together with yesterday's port guard, the two descriptions of a
component can no longer disagree about a port name or a required parameter without a test saying
so.

Item 4 (the document builder guessing a block's domain instead of reading it) is in `document`
rather than `compile` and stays open on the issue.

The sweep's two remaining `KNOWN_BROKEN` entries are now annotated for what they are: `sum` and

structural sweep does not run, so it has nothing to drive. That is the harness's gap rather than

## 2026-11-20 18:35 — the tier sweep was not checking what it said (#65)

Found while adding the boundary ports in #63 and filed rather than folded into it.

`library_compiles_at_every_tier` treated an empty netlist as a failure. The netlist is never
empty: the emitter always writes its two-line banner, so a one-block document that emitted
nothing at all came back 119 bytes long and counted as compiled. For a `structural` type the
sweep was asserting only that `compile()` returned `Ok`.

Counting non-comment lines instead is the obvious fix and it is wrong, which is worth recording
because I wrote it first. **The harness adds blocks** — one `source.const` per signal input, a
ground for a physical pin — and their cards are non-comment lines too. A structural block with
one driver yields exactly one card, and it is the driver's. The question has to be asked about
the block under test: `cards_naming(&netlist, "dut")`.

Two more things that only showed up by running it:

- `universal_components.rs` matches a card to a block with
  `trim_start_matches(char::is_ascii_alphabetic)`, to undo the single device letter
  `element_name` prefixes. That works there only because every block id it checks carries a
  digit (`g1`, `scope1`). `dut` is all letters, so trimming leaves the empty string and nothing
  ever matches — **32 components reported as emitting no card** when every one of them emits a
  good one. One letter is what the emitter adds, so one letter is what comes off.
- A composite emits several cards, each `<letter><id>_<part>`: a transformer is `Edut_sec` and
  `Fdut_pri`. Three components are composites and all three were then reported as silent.

Both arms are now asserted rather than one exempted. A structural type must emit **no** card of
its own — emitting one would mean `Scope::emittable` had leaked, which `universal_components.rs`
guards from the other side — and everything else must emit at least one. Verified by pretending
a resistor is structural (3 tiers named) and that a Goto is not (named).

91 (component, tier) pairs, up from 85 with the two boundary ports.

found a regression that the decision record's own reasoning had invited.

library entry, `routing.junction` and `spice-subckt.boundary` do not. By that rule
`hierarchy.inport`/`hierarchy.outport` were correctly removed — nobody places one, grouping

```ts
if (crossingWires.length > 0 && (!inportMeta || !outportMeta)) return null;
```

So **Ctrl+G silently did nothing whenever a wire crossed the selection**, which is the ordinary

`hierarchy.subsystem.virtual`, which this engine has no `TypeSpec` for. Ctrl+G stops being a

## 2026-11-19 02:01 — what a fidelity tier is, written down

[#38](https://github.com/GLODI-Engineering/gsim-core/issues/38). `"tier"` appears 287 times in
`data/component-library.json` and in no README or `AGENTS.md`. The only prose about it was in
decision 0003 — a record that is now superseded, so the one explanation a reader could find was
inside a document they should be told to discount.

Measured from the library before writing any of it down: four tiers in use across 239
components — `ideal` (189), `n_a` (50), `behavioral` (31), `spice` (17); 208 components offer one
tier, 14 offer two, 17 offer three. `passive.capacitor` is the example that makes the point,
because its `ideal` tier carries `C` and `IC` while `behavioral` and `spice` carry only `C`.

The three facts a reader needs, now in the README under "Fidelity tiers" and as invariant 6 in
`AGENTS.md`:

- a component declares `ports` and `params` once **per tier**, not once with views over it;
- a block records its tier (`Block::fidelity`, defaulting to `"ideal"`, so an older `.gsim_sch`
  loads as ideal), and switching tier **removes** the parameters the new tier does not list — a
  capacitor moved off `ideal` loses `IC` from the document rather than hiding it;
- the compiler never branches on the tier, so a tier omitting a parameter the registry requires
  is a component that compiles until the user touches the dropdown, which is exactly what
  `tests/library_compiles_at_every_tier.rs` exists to catch.

## 2026-11-18 (2) — Two nets could emit under one node name (#30)

The same hole as #28, one layer down, and worse. `nets::resolve_scope` named each net and never
compared the number of nets with the number of names. Three sources share that namespace — a
`.SUBCKT` boundary port, a user's `wire.net`, and the generated `n_<block>_<port>` — and
`sanitize` maps every non-alphanumeric character to `_`, so `V-OUT` and `V_OUT` are one emitted
name. Two roots resolving to one name simply wrote the same string into both of `NetScope`'s maps:
`names: BTreeSet` absorbed the duplicate and every endpoint of both nets reported the same node.

Why it is worse than the element case: there, two devices shared a name and the voltages were
still right, because stamping is positional. Here two *separate nodes* become one node, which is a
short circuit the author never drew, and the numbers that come out are wrong.

Refused now, at the point the names are assigned, with each net identified by its ports — a net
has no id of its own, so there is nothing else a reader can look for on the sheet:

```text
node name 'V_OUT' is claimed by two separate nets -- one reaching C1.p1, R1.p2, the other
reaching C2.p1, R2.p2 -- so they would be emitted as one node and shorted together.
```

`resolve_scope` therefore returns `Result`, and `build_scope`/`heuristic_reference` carry it.

**The one name many nets may share is `0`.** Several independent grounds are all the reference
node, so excluding it is not an exception to the rule — being the reference *is* being the same
node. A test pins that down, next to one pinning the false positive to avoid: a star net has many
endpoints and one root.

**Verification.** The CI gate set, 211 + 3 + 28 + 2 + 1 + 32 tests (4 new), fmt and clippy clean.

## 2026-11-18 — One name per drawn object, and the map back from the netlist (#28)

Found from the far end of the pipeline. Designing the contract between the simulator's output
and the GUI, the first question is identity: an event says `target: "Rload"`, a result column
says `V(n_Rload_p2)`, and the front end holds block ids. Which block is `Rload`?

`CompileOutput` could not say — it carried `netlist` and `notes` — and the front end cannot work
it out either, because `element_name` is **not injective**:

```rust
element_name("load", 'R') == element_name("Rload", 'R') == "Rload"
```

A sheet with both blocks compiled, with `notes: []`, to

```text
Vdc n_Rload_p1 0 10
Rload n_Rload_p1 n_Rload_p2 10
Rload n_Rload_p2 0 20
```

Two elements of one name, and the second resistor's own terminals named after the *other* block,
so reading the netlist by hand misleads too. The solver accepted it (`general-mna` rejected a
duplicate name only for device letters whose name becomes an unknown — filed and fixed there as
GOTCHA-001, 0.5.1) and the voltages were right: 6.667 V, the correct divider. Stamping is
positional and never looks a name up.

What is lost is every reference **by** name: a rating on the device line, a `kind=rule` card's
`target=`, a `kind=measure`, a controlling branch, a `.IC`, the front end's highlight. Each
resolves to one of the two devices, by iteration order, and nobody is told the other exists.

**Both halves are now in `compile::provenance`.** One pass claims a name per document object,
per netlist namespace, refusing a second claimant with both block paths and the reason two
different ids can collide. The same pass records the map it had to build anyway:

```json
{"element": "Rload", "blocks": ["load"], "role": "element"}
{"net": "n_Rbot_p1", "ports": [{"blocks": ["Rload"], "port": "p2"},
                               {"blocks": ["Rbot"], "port": "p1"}]}
```

Names are the **flattened** ones an engine actually reports — `X1.Rin`, not the body-local `Rin`
— including the boundary substitution an `X` card performs on its def's nets, so a net inside an
instance resolves to the parent's own node where it crosses the boundary.

Three cases the check must *not* reject, each pinned by a test: an ideal switch, whose element
card and `kind=` card share one name by design (`general-mna` joins them by name); a composite,
whose expansion emits several cards that are all one drawn block (`ET1_sec`, `FT1_pri`); and two
instances of one `.SUBCKT`, whose bodies hold two blocks of the same body-local name in different
namespaces.

**Verification.** `cargo fmt --check`, `cargo clippy --workspace --exclude gsim-py --all-targets
-D warnings`, `cargo clippy + test -p gsim-py --no-default-features`, `cargo test --workspace
--exclude gsim-py` (207 + 3 + 28 + 2 + 1 + 32), `cargo doc`. Then end to end through a freshly
`maturin develop`-ed `gsim_py`: the colliding sheet is refused with `duplicate-name: ...`, and the
same sheet with distinct names returns the provenance above.

**Found but not done:** net names have the same hole. `resolve_scope` never checks that two
distinct nets got distinct emitted names, and `sanitize` collapses characters (`V-OUT` and
`V_OUT` both become `V_OUT`), so two nodes can merge into one — a short circuit, silently. Filed
separately rather than folded in here, since it belongs in `nets.rs` and changes that function's
signature.

## 2026-11-06 06:10 — Two ways the compiler emitted a name the engine does not have (#1, #2)

Both issues are the same failure class, found from the other end: a schematic that compiled
cleanly into a netlist naming something the engine never registers. One of the two was silent,
which makes it the worse of the pair by a wide margin.

**#1 — `ref_name`'s fallback to the peer block's own name.** `Scope::ref_name` ended with

```rust
.unwrap_or(peer.block.as_str())
```

so a `field=` reference whose wire landed on a peer **input** port — no recorded output name —
rendered as that peer *block's* name. A block name almost always exists, so nothing failed:
the netlist loaded, the engine ran, and it simulated a circuit nobody drew.

Found while drawing a bidirectional switch pole: one gate driver into the first pole's gate,
then gate-to-gate to share the drive. That emitted `ctrl=DS1B` on the second pole — `DS1B` is a
real block — so both poles were controlled by the wrong thing with no diagnostic anywhere. It
was caught by reading the emitted netlist by hand, which is not a review step anyone should
have to perform.

Now `CompileError::RefNotAnOutput`, naming both ends and what to do instead (fan out from the
driver's output, the convention `examples/h_bridge_3phase.py` already establishes). Nothing in
the crate relied on the fallback: 177 unit tests and all ten `examples/` scripts pass and
regenerate byte-identical `.cir` files.

One path it newly rejects is worth recording, because it was *already* broken and this only
makes it visible: a downstream reference to a **subckt instance's** signal output port. Those
blocks carry no `TypeSpec`, so no output name is recorded for them, and the old fallback emitted
the instance's block id while the X card is named `X<id>` — a name that does not exist either.
Giving an X card's signal outputs real names is a design question of its own, left open; it has
no fixture and no example today.

**#2 — a declared `outputs[0]`.** `Outputs::record` let a user-supplied `outputs` parameter name
index 0. Verified against a real engine run rather than inferred:

```text
SRC kind=const value=3
BLK kind=pyblock path=two.py in=SRC outputs=AAA,BBB
G1  kind=gain k=2 in=AAA
```

→ `error: UnknownBlockInput("AAA")`, while the same netlist's CSV header comes out as
`t,SRC,BLK,G1,BBB`. The engine registers a multi-output block's first output under the block's
own card name and reads only `outputs[1..]` from the list, so `AAA` never exists at all. The
doc comment on `Outputs` already stated that rule; the code then let the parameter override it.

Index 0 is now pinned to the card name, and the override is reported through `CompileOutput.notes`
rather than dropped in silence — the user wrote that name expecting to use it, and should be told
which name to use instead.

**Not done, deliberately:** the engine side. `general-mna` ignoring `outputs[0]` without
complaint is the mirror image of this bug, but that repo is a read-only path dependency here
and `general-simulator`'s own `AGENTS.md` requires explicit confirmation before editing it.

--all-targets -D warnings`, `cargo clippy + test -p gsim-py --no-default-features`,
`cargo test --workspace --exclude gsim-py` (177 + 28 + 2 + 32), plus all ten `examples/`
scripts re-run through a freshly `maturin develop`-ed binding.
