## 2026-11-06 06:10 — Two ways the compiler emitted a name the engine does not have (#1, #2)

Both issues are the same failure class, found from the other end: a schematic that compiled
cleanly into a netlist naming something the engine never registers. One of the two was silent,
which makes it the worse of the pair by a wide margin.

**#1 — `ref_name`'s fallback to the peer block's own name.** `Scope::ref_name` ended with

```rust
.unwrap_or(peer.block.as_str())
```

so a `field=` reference whose wire landed on a peer **input** port — no recorded output name —
rendered as that peer *block's* name. A block name almost always exists, so nothing failed:
the netlist loaded, the engine ran, and it simulated a circuit nobody drew.

Found while drawing a bidirectional switch pole: one gate driver into the first pole's gate,
then gate-to-gate to share the drive. That emitted `ctrl=DS1B` on the second pole — `DS1B` is a
real block — so both poles were controlled by the wrong thing with no diagnostic anywhere. It
was caught by reading the emitted netlist by hand, which is not a review step anyone should
have to perform.

Now `CompileError::RefNotAnOutput`, naming both ends and what to do instead (fan out from the
driver's output, the convention `examples/h_bridge_3phase.py` already establishes). Nothing in
the crate relied on the fallback: 177 unit tests and all ten `examples/` scripts pass and
regenerate byte-identical `.cir` files.

One path it newly rejects is worth recording, because it was *already* broken and this only
makes it visible: a downstream reference to a **subckt instance's** signal output port. Those
blocks carry no `TypeSpec`, so no output name is recorded for them, and the old fallback emitted
the instance's block id while the X card is named `X<id>` — a name that does not exist either.
Giving an X card's signal outputs real names is a design question of its own, left open; it has
no fixture and no example today.

**#2 — a declared `outputs[0]`.** `Outputs::record` let a user-supplied `outputs` parameter name
index 0. Verified against a real engine run rather than inferred:

```text
SRC kind=const value=3
BLK kind=pyblock path=two.py in=SRC outputs=AAA,BBB
G1  kind=gain k=2 in=AAA
```

→ `error: UnknownBlockInput("AAA")`, while the same netlist's CSV header comes out as
`t,SRC,BLK,G1,BBB`. The engine registers a multi-output block's first output under the block's
own card name and reads only `outputs[1..]` from the list, so `AAA` never exists at all. The
doc comment on `Outputs` already stated that rule; the code then let the parameter override it.

Index 0 is now pinned to the card name, and the override is reported through `CompileOutput.notes`
rather than dropped in silence — the user wrote that name expecting to use it, and should be told
which name to use instead.

**Not done, deliberately:** the engine side. `general-mna` ignoring `outputs[0]` without
complaint is the mirror image of this bug, but that repo is a read-only path dependency here
and `general-simulator`'s own `AGENTS.md` requires explicit confirmation before editing it.

**Verification.** `cargo fmt --check`, `cargo clippy --workspace --exclude gsim-py
--all-targets -D warnings`, `cargo clippy + test -p gsim-py --no-default-features`,
`cargo test --workspace --exclude gsim-py` (177 + 28 + 2 + 32), plus all ten `examples/`
scripts re-run through a freshly `maturin develop`-ed binding.
